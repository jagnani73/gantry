# Gantry — Project Guide

Hackathon project for NTU InnovateX 2026 (Track 1: Payments & Financial Infrastructure). Solo builder (NTU student, Student Group entry). This file is the canonical context for working sessions — read it fully before building.

## What Gantry is

A payer-agnostic payment rail on stablecoins. One on-chain `PaymentIntent`, one settlement contract, two doors:

- **Human door:** printed static QR encodes `…/pay/<handle>` → mobile payer page → payer signs an EIP-3009 `transferWithAuthorization` (gasless — tourist needs zero ETH) → relayer settles.
- **Agent door:** HTTP `402 Payment Required` with x402 v2 `PAYMENT-REQUIRED` header; `accepts[]` offers the standard `exact` scheme (any vanilla x402 client can pay) AND a custom `gantry-pbm` scheme (agent session key EIP-712 sig, executed through an on-chain policy wallet).

Both settle through `GantryCore._settle()`: pull funds → swap to XSGD if needed (min-out guard) → pay merchant → emit `IntentSettled`. Merchant dashboard shows both payer types landing in one live feed. That convergence IS the thesis — never build anything that exists for only one door except the thin encoding layers.

**Pitch line:** "x402 standardized how machines pay. Gantry is the rail that lets one merchant accept payments from machines and humans alike."

**Framing is strictly Singapore-centric:** XSGD settlement, hawker/tourist scenes, PayNow's structural gaps (no foreign payers, no agent payers), PBM framing after MAS Project Orchid.

## Architecture (decided — do not relitigate without user)

**Contracts** (`packages/contracts`, Foundry, Solidity ^0.8.24, OZ only for ERC-20/Ownable). **OpenZeppelin comes from npm** (`package.json`, pinned exact to 5.7.0), not `forge install` — OZ's own docs warn a git install can silently follow the unreleased `master` on update, while a published npm version is immutable. Remappings live in **`remappings.txt`, which shadows any CONFLICTING prefix in `foundry.toml`** — a prefix defined only in `foundry.toml` still applies, but one defined in both resolves from `remappings.txt`, so put mappings there to avoid guessing (verified in a scratch project). `forge-std` stays a submodule (test-only, no npm distribution), so a fresh clone needs `git submodule update --init`. (`--recursive` used to be actively harmful because it pulled OZ's own test submodules; now that OZ is an npm dependency it is merely a no-op, since forge-std has no submodules of its own.) Switching the OZ path changed no executable code (proven: identical source under both layouts with metadata disabled builds byte-identically) but did change the embedded metadata hash, so a fresh build no longer byte-reproduces the deployed bytecode; the on-chain contracts and their Basescan verification are unaffected:
- `GantryCore.sol` — merchant registry (`registerMerchant(handle, payout, categoryId)` = the 2-min onboarding, plus `setMerchantPayout` rotation gated on the current payout), `PaymentIntent` lifecycle, `settleWithAuthorization()` (QR + x402 `exact`; **EIP-3009 `nonce` must equal `intentId`** — binds signature to intent) and `settleFromPBM()` (Agent-door intents only); shared `_settle` with reentrancy guard, 0.5% protocol fee skim (`feeBps=50`, capped 2%); custom errors; `IntentSettled(intentId, merchantId, payer, tokenIn, amountIn, xsgdOut, feeXsgd, door)` — xsgdOut is gross, merchant receives xsgdOut − feeXsgd. Ownable2Step, renounce disabled.
- `AgentPBMWallet.sol` + factory — `owner` (human) funds it and sets `Policy {dailyCap, perTxCap, expiry, categoryBitmap}`; `agentSigner` is the agent's session key. `authorizeSpend()` (onlyCore) verifies EIP-712 sig + all policy dimensions + daily window. Custom errors `PerTxCapExceeded`, `DailyCapExceeded`, `CategoryNotAllowed(uint16)`, `PolicyExpired` — these exact names surface in the demo; facilitator returns them as x402 `invalidReason`.
- `FixedRateSwap.sol` (owner-set rate, seeded 1.3421) behind the `IGantrySwap` interface — this is what ships. **`GantrySwap.sol` (x·y=k AMM) is SKIPPED by decision (7 Aug 2026)**: do not build, deploy, or wire an AMM unless the user explicitly asks. The seam is the point — production FX means real XSGD liquidity via aggregator/RFQ behind the same interface, not a toy pool. Label the demo rate as owner-set everywhere.
- `MockXSGD.sol` (and `MockUSDC.sol`, now deployed-but-unused — the app moved to real Circle USDC on 7 Aug 2026; **removed from `addresses.ts` and from every deploy script's minting on 8 Aug 2026**, it survives only as the Foundry suite's generic EIP-3009 test double and as the historical address in the table below) — both extend a shared hand-written `EIP3009` base (FiatToken-shaped: typehashes, `authorizationState`, events), 6 decimals, open mint. XSGD carries EIP-3009 deliberately: real XSGD supports x402 natively (StraitsX), and XSGD-direct settlement flows through the same authorization door. XSGD exists on NO testnet — mock is the honest option; label it.
- Primary pay token on Sepolia: Circle's real testnet USDC `0x036CbD53842c5426634e7929541eC2318f3dCF7e` (implements EIP-3009, has faucet). Fork-test against it from the start — EIP-3009 domain/sig quirks are a known risk.

**Backend** (`packages/backend`, Node 22 + Express + viem): merchant API; x402-protected routes via `@x402/express` pointed at our own facilitator; facilitator `/verify` + `/settle` (spec-shaped, `@x402/core` types, hand-rolled `gantry-pbm` handler); relayer (holds the only gas key — payers never send transactions); SSE indexer via `watchContractEvent` over WebSocket RPC; paged read surface for the two UI surfaces (`GET /api/settlements`, `/api/denials`, `/api/agents`). The `merchant_profiles` exception went away on 11 Aug 2026 when the display record moved into `GantryCore`. **Web** (`packages/web`, Next.js 15 App Router + Tailwind v4 + wagmi v2 + RainbowKit): **two surfaces plus a landing page, light-only** — the `.dark` class and every dark variable are deleted. **Brand mark** (added 9 Aug 2026): a portal frame with two ramps running out from under it — the two doors converging on one rail. It is drawn in the existing tokens (ink, accent, accent-tint), so it was adopted as-is rather than recoloured. The geometry lives in ONE place, `primitives/gantry-mark.tsx`, traced from the source artwork into three flat paths that paint through `fill-*` utilities — hence no hex in the component, and hence it repaints with the design system. Every icon under `src/app` (`icon.svg`, `favicon.ico` 16/32/48, `apple-icon.png`) and `public/` (`icon-192`, `icon-512`, `icon-maskable-512`, wired by `src/app/manifest.ts`) is **generated from those same three paths**: change the component without regenerating and the tab icon silently disagrees with the page. Do not "fix" either by inventing one. `docs/brand/` carries the bare glyph for the deck and Devpost. **There is no OG/social image yet** — the wordmark would need Instrument Sans, which `next/font` only fetches at build time, and a link preview set in the wrong typeface is worse than none.

**Agent** (`packages/agent`, Vercel AI SDK `ai` + `@ai-sdk/google`, model `gemini-flash-latest` — Google AI Studio free tier; switched from `@anthropic-ai/sdk`/claude-opus-5 on 7 Aug 2026, zero-budget decision): terminal CLI; tools `list_merchants`, `check_my_policy`, `pay_merchant` (deterministic HTTP + signing inside the tool; the LLM narrates via `streamText` multi-step tool loop). 8s LLM timeout → scripted reasoning fallback, visually identical. **No wallet address in its config:** it derives its signer from `AGENT_SESSION_KEY` and discovers the wallet it acts for via `GET /api/agents?agentSigner=` — wallet addresses became dynamic once payers create them, and the CLI knows only its own key. ## Canonical demo facts (bake into seed data / `demo-reset` script)

- Merchant: **"Ah Hock Chicken Rice"**, Maxwell Food Centre, category `food_beverage`.
- Human payment: **iced tea S$1.50** → 1.117652 USDC → 1.50 MockXSGD @ 1.3421.
- Agent payment: **3 iced teas for the team = S$4.50** (3.352955 USDC).
- Prices are hawker-drink scale on purpose: settlement is in REAL Circle USDC now, which is finite, and S$1.50 is a real drink price so the Singapore framing survives. A full run costs ~4.5 USDC.
- Agent policy: S$50/day cap, categories `[food_beverage]`, 30-day expiry, revocable.
- Rejection beat: "GadgetHub SG" (`electronics`), **S$4 phone cable** → on-chain revert `CategoryNotAllowed`. Cheap on purpose: it is *inside* every cap the wallet has, so the only thing that can stop it is the category — "the amount was fine, the category wasn't". It also has to be affordable, because the facilitator's balance pre-check runs BEFORE the on-chain policy check: price it above the wallet's balance and the beat dies as `insufficient_funds`, which is the wrong story entirely (this is why `demo-reset` tops the wallet to 10 USDC).
- Fee story: on the day's **S$6.00**, Gantry takes **S$0.03** and cards would take **S$0.168**. Narrate it as a rate against real volume, not a day's total — "three cents on six dollars; a hawker doing S$2,000 a month pays S$10 with us and S$56 with cards". **Trap:** the Overview screen's **Saved vs cards** tile renders **S$0.13**, which was the OLD number for Gantry's cut — do not say "we took thirteen". The three tiles are *Collected, last 7 days* (net, **S$5.97** on demo day), *Paid by* (an agent/human split bar over payment COUNTS, not money) and *Saved vs cards* (**S$0.13** = card fee − our fee, clamped at zero); the gross and the card fee are never on screen. **The tiles cover a ROLLING 7-day window, not a day and not a calendar week** (changed 10 Aug 2026): `OVERVIEW_WINDOW_DAYS` in `feed-state.ts`, start day from `minusDaysKey`, pinned to SGT. Rolling specifically because a calendar week empties itself at its own boundary — on a Monday morning "this week" reads zero though the shop traded all weekend, and a merchant cannot tell that from a dead feed. Demo figures are unaffected, since every payment in a run lands the same day. Two consequences: the "loaded so far" partial warning now fires routinely (7 days hold ~7× the rows one page carries, so **the "Load older" button beside it is load-bearing, not an edge case** — it fires whenever a full 50-row page fits inside the window, which is the normal case on the demo book), and the sidebar's Overview count is the window's.
- **Merchant display facts are ON-CHAIN** (since 11 Aug 2026). `GantryCore.Merchant` carries `displayName`, `location` and `blurb` beside handle/payout/category; there is no `merchant_profiles` table and no seed fallback anywhere — an absent field renders as nothing rather than as an invented name. `demo-reset` registers the canonical shops from `DEMO_MERCHANTS` in `packages/shared/src/constants.ts`, which is now the *input to a chain write* rather than a table the backend fell back to; `DEMO_MERCHANT_HANDLE` is the one shop every handle-less link falls back to.
- `demo-reset` = one command, Sepolia-based: top up the funder, fund the demo payer, register the canonical shops on-chain, provision/top up and re-arm the demo agent, check gadgethub-sg is registered; contracts persist and the relayer holds gas ETH. It waits on real receipts (the "<1s" figure predates M3) and must stay **<30s**: that budget is what enables rehearsal. **It does not touch the transaction feed and cannot** (11 Aug 2026) — the name is legacy; it provisions money, merchants and policy, nothing else. **A clean book is a fresh core, `pnpm contracts:fresh`.** **The re-arm is signed by the demo PAYER's key, not the relayer's** — `setPolicy` is `onlyOwner` and agent wallets are payer-owned, so nothing on the server can arm a policy any more. **The 30s register cooldown is in-process and survives `demo-reset`** — back-to-back onboarding takes inside 30s will 429; restart the backend between them. Redeploying contracts is a DIFFERENT script, `pnpm contracts:fresh`, run by hand and never before a demo.

## Status: M2 complete + review-hardened (6 Aug 2026)

The x402 agent door is live end-to-end on Base Sepolia: `POST /api/order/:handle?sgd=…` 402-challenges with a spec-shaped v2 `PAYMENT-REQUIRED`, an **unmodified vanilla `@x402/fetch` client pays it** (the interop beat), and the settlement lands in the same dashboard feed as QR payments with the Agent badge. The M2 review gate ran (5 agents); all agreed findings fixed. Tests: 21 shared + 20 backend, plus live e2e (curl decode, vanilla buy, SSE both-doors, replay/tamper/broke-payer reasons).

**The load-bearing M2 discovery:** vanilla x402 v2 `exact` clients random-generate the EIP-3009 nonce (`createNonce()` in `@x402/evm`; no pinning extension), but the frozen core hardcodes `nonce = intentId`. A literally-unmodified client can therefore never sign what `settleWithAuthorization` settles. **User-approved design: the facilitator bridge** — accepts[] is 100% spec-standard with `payTo = relayer`; at settle the bridge creates the Agent-door intent, collects the agent's authorization onto the relayer (`transferWithAuthorization`, no pre-float), relayer self-signs an EIP-3009 auth with `nonce = intentId`, and settles via the M1 `settlement.settle()`. On-chain payer is the relayer (one custodial hop, PSP-style — on the honest-labels list); the agent's address travels in `PAYMENT-RESPONSE` and on SSE rows as `agentPayer` (“via facilitator” in the UI).

**What exists:** `packages/shared/src/x402.ts` (owned v2 wire types + base64 header codec, zero `@x402` imports — churn insurance; `Caip2Network` template type keeps the SDK boundary compiler-checked) and `abis/eip3009Token.ts` (hand-written collect/refund ABI fragment). Backend: `services/facilitator-core.ts` (pure, config-free: payload schema, `validateExactPayment`, `parseOrderPins`, `splitSignature65`, `reasonForGantryError`), `services/facilitator.ts` (verify + chain reads with a bounded balance-lag retry — same replica-lag class M1 retries in settle), `services/bridge.ts` (the bridge + outcome resolution), `routes/facilitator.ts` (spec HTTP surface: GET `/facilitator/supported`, POST `/verify`+`/settle`, in-band failures), `routes/order.ts` (DynamicPrice + receipt handler), `src/x402.ts` (`@x402/express` middleware wired to an **in-process** `FacilitatorClient` — the SDK syncs `/supported` at construction pre-listen, and its HTTP client's default 30s timeout can't cover three serialized txs). `scripts/x402-buy.ts` = the vanilla-client proof (`pnpm --filter @gantry/backend x402:buy`). Deps pinned exact `@x402/{core,evm,express,fetch}@2.21.0`. The order token is real Circle USDC, hardcoded — `ORDER_TOKEN` was removed with MockUSDC on 7 Aug 2026, and `x402:buy`'s fresh burner is funded by the same relayer transfer as the human door.

Design notes that bind M3/M4:
- **Trust channel:** the bridge's order facts (`handle`, `xsgdAmount`) come ONLY from server-pinned `requirements.extra` (the SDK subset-matches extra against the client echo; the client-echoed `resource.url` is never load-bearing — a client could echo another merchant's URL at the same price). Any new scheme handler must follow this rule. *(M3's pbm handler follows it.)*
- **Compensation invariant:** never assume "the relayer helper threw ⇒ the tx did not happen" — receipt timeouts leave broadcast txs that may mine. The bridge proves outcomes on-chain before refunding: `authorizationState` reads + the cancel-tx nonce-ordering trick (a cancel that lands proves the stuck tx was consumed; `IntentAlreadySettled` on cancel proves settlement won). Unresolved outcomes get CRITICAL logs with manual-recovery data, never blind refunds. *(M3's pbm settle wrapper inherits this.)*

Design notes that bind later work:
- **`agentStatus()` is the only correct way to badge a policy** — tri-state `active | lapsed | revoked`. `revoked` is derived from `expiry === 0`, so a *naturally lapsed* policy (`0 < expiry < now`) denies every spend while `revoked` stays false; re-deriving the badge by hand renders a dead policy as "Active". The comparison is pinned to `authorizeSpend`, which reverts when `block.timestamp > expiry` — so `expiry` is the LAST second a spend is allowed and `now === expiry` is still active. Pass chain time when you have it: a laptop minutes fast would badge a working policy "lapsed".
- **The agent daily window rolls at `block.timestamp / 1 days` — UTC days, i.e. 08:00 SGT**, not local midnight. Any copy explaining the cap must say "resets 08:00 SGT".
- **Never hand viem a bare address as an explicit `account` on a client that signs locally** (found 10 Aug 2026, and it had broken every browser-signed owner write since payer-owned agents landed). An explicit `account` OVERRIDES `client.account`, and `parseAccount` reads a string as a **json-rpc** account — the signal for "the node holds this key" — so `writeContract` called `eth_sendTransaction` against a plain HTTP transport and `sepolia.base.org` answered `unknown account`. `simulateContract` only reads `.address`, so simulations pass and the failure looks like an RPC fault. `agent-writes.ts` therefore returns the CLIENT and no separate account, and every call site passes `client.account`. Nothing in the sign-off gate covers this: `demo-reset.mjs` had the correct pattern all along, so it proves the demo KEY can arm a policy, never that the browser can — **create agent → arm → revoke must be exercised by hand in the browser**.
- **`waitForTransactionReceipt` without `onReplaced` silently resolves with a DIFFERENT transaction's receipt** — it scans for one with the same `from` and `nonce` and returns that. On the shared demo key, where every visitor of a deployed build signs as one account, that is a routine collision rather than an exotic one: it would grade a stranger's transaction as our success, and `createWallet` would parse the stranger's logs and hand back their wallet address. Every browser wait passes `onReplaced` and raises `UnknownOutcomeError` — unknown, never failed, because ours never mined.
- **A write the payer signs is confirmed against a DIFFERENT provider than the read that follows it** (10 Aug 2026). The browser waits for its own receipt on its own RPC; every screen then re-reads through the backend, which uses its own fallback chain — so a read issued milliseconds later is routinely served by a replica without the block, and the payer is returned to a screen still showing the rules they just changed, which is indistinguishable from the write doing nothing. The browser holds a mined receipt for the policy it sent, so any read that disagrees is behind: `policyFingerprint` (the four stored fields, never `spentToday` or the balance, which move on their own) is recorded through `expectAgentPolicy` and the detail screen re-reads on a bounded poll until it matches. Same discipline as the payer store's balance watch. It applies to **revoke** too, where a stale read leaves a chip saying "Active" over a wallet that now reverts everything. **Known-superseded data is not rendered at all** while that wait runs — the detail screen falls back to the store's agent list when its own read has not landed, so without the gate the first paint after a save is the OLD policy, which then silently becomes the new one under the payer. A frame that states the wrong caps is a claim about the chain, and a brief "Your change is on-chain. Reading it back…" is the honest version of the same second.
- **An agent's name and its policy date are ON-CHAIN, and the factory was redeployed for them (10 Aug 2026).** `AgentPBMWallet` gained `string label` (owner-set, taken by `createWallet` so naming costs no transaction of its own) and `uint40 policyUpdatedAt` (written by the one internal path `setPolicy` and `revoke` share, so a revoked wallet dates from its revoke). `policyUpdatedAt` packs beside `_lastSpendDay`/`_spentToday` — 64+128+40 bits, slot 7 offset 24, verified with `forge inspect AgentPBMWallet storage-layout` — so `_setPolicy` still writes the day bucket, the counter and the stamp in one SSTORE. It is out of the `Policy` struct **for the calldata, not for the storage**: a member there rides in `setPolicy(Policy calldata)` as a caller-supplied field the contract immediately overwrites. (Storage was not the reason, and an earlier version of this note wrongly said it was — `expiry`'s slot has 27 spare bytes because `categoryBitmap` needs a whole slot regardless, so a `uint40` inside the struct would also have been free. A reader "optimising" on the false premise would move the field and reintroduce the calldata wart.) Both replaced worse answers: the label was a localStorage map, invisible on any other device and so doubly wrong on a build where every visitor shares one demo key; the date was a bounded backwards log scan that could not answer for a policy older than the window it searched. **The field is `label`, never `name`** — `DOMAIN_SEPARATOR()` hashes the literal `"AgentPBMWallet"`, and a `name()` getter beside it invites wiring the two together, which would kill every agent signature the moment an owner renamed. **31 BYTES, not characters** (`bytes(label).length`, the inline-string bound): eight 4-byte emoji are already over, so a client counter that measures codepoints — as `profileFieldLength` deliberately does for merchants — would offer a label the contract refuses. Renaming an existing wallet is its OWN transaction: `setPolicy` must not carry it, because that call resets the daily counter and a rename must never cost the agent its budget. A redeploy orphans every wallet the previous factory made — they still work, nothing lists them — which is accepted whenever the wallet ABI changes, since a factory can only mint what it was compiled against. Reads of the two new getters degrade to `""`/`0` rather than marking a wallet unreadable, so an old wallet's policy can still be read and revoked.
- **A mined deploy is proof, and a visibility poll after it is best-effort.** `AgentPBMWalletFactory.createWallet` has no idempotency — it pushes a fresh wallet on every call — so a throw after the receipt drops an address that exists on-chain, and the caller's retry mints a SECOND wallet for the same signer. Return the address even when the follow-up read cannot see it yet.
- **A denied payment has no reverted transaction.** The revert is caught by simulate-before-send and never broadcast, so the only hashes that exist are the intent-creation tx and the cancel tx. A declined receipt reads "Cancelled · 0x…" from `cancelTxHash` and "Moved: Nothing"; when the cancel itself failed, render no hash at all rather than inventing one. The error name travels **verbatim** (`CategoryNotAllowed`) — the UI may explain it alongside, never instead of.
- **`payer` on `/api/settlements` is a comma-separated list and matches `payer` OR `agentPayer`.** A PBM payment's on-chain payer is the wallet, not the human, so filtering on the human's address alone would hide exactly the rows the agents screen exists to show.
- **Alchemy's free tier caps `eth_getLogs` at TEN blocks** (measured 8–9 Aug 2026; an earlier comment claimed 10k). Every 1,999-block sweep chunk is therefore rejected by the paid primary and served by `sepolia.base.org` — two RPC calls per chunk, and **the rate-limited public node is what actually carries the correctness path**. Raising the chunk wedges the sweep entirely (the cursor never advances); dropping it to 10 turns a cold backfill into thousands of calls. The same constant and the same reason govern the factory scan in `services/agents.ts` and the registration-date scan in `services/merchants.ts`.
- **An RPC rate limit belongs to the EGRESS IP, not to the endpoint** (measured 9 Aug 2026, after the deploy). The factory scan in `services/agents.ts` — 54 chunks at concurrency 4 — completes against `sepolia.base.org` from a laptop with zero failures in ~5.7s, and dies on Render after ~48 chunks in 1.8s with "over rate limit" from that same endpoint. So any concurrency constant tuned on the laptop is a throughput choice and never a safety mechanism, and "swap to a better provider" is unfalsifiable from here: publicnode and tenderly also passed cleanly from the laptop, which proves nothing about Render's shared IP. What actually holds is `runRanges` + `RETRY_BACKOFF_MS` (retry ONLY the failed chunks, 750/1500/3000ms, whole scan idle through the wait — viem's own 3× 150/300/600ms retry loses because it backs off while the rest of the batch keeps firing, which is exactly when a token bucket cannot refill) and `scanCursor` in agents-core (a partial scan keeps the ground it covered, so a retry finishes the tail). Without that cursor the failure is self-sustaining: a throttled scan discarded every chunk that succeeded, and the payer's retry re-fired all 54 into an empty bucket — a page that should be slow was permanently broken instead. **The remaining structural fix is to fold `WalletCreated` into the indexer's persisted sweep** (`getLogs` takes an address array, so both contracts cost the calls the indexer already makes): the agents scan currently re-walks the same block span the indexer already walks, and it grows ~22 chunks/day — ~310 chunks per cold process by the finals, on a free tier that spins down so most visits are cold.
- **The merchant registration date is a bounded, resumable, amortised log walk**, started only by display requests (`waitForRegisteredAt`) and never by the payment path — and a merchant registered *through* this backend skips it entirely, because the block its tx mined in is the date. An absent date renders as nothing; an estimate would be worse, since this is the fact a shop would cite as proof it existed.
- **`PATCH /api/merchants/:handle` is unauthenticated by decision**, so it carries the same `NODE_ENV` host-class gate as self-service onboarding plus a 10s per-IP cooldown; a valid `x-admin-token` means an operator (demo-reset seeding) and is exempt from both. Do not paper this over with a login that checks nothing.
- The merchant's first screen is **Overview**, not Settlements (renamed 9 Aug 2026). Both it and Transactions list settlements, so two nav items called "Settlements" and "Transactions" told a merchant nothing about which one they wanted. Overview is the last seven days at a glance plus the live feed; Transactions is the whole book, searchable and exportable. The route is `/merchant/[handle]/overview` and `DEFAULT_SCREEN` points at it. **The `/api/settlements` endpoint, `SettlementEvent`, `settlementsCsv` and the payer store's `settlements` did NOT rename** — those name the data, which is still settlements, and collapsing the two vocabularies would lose the distinction the rename was made to draw.
- **Shop profile and Settings were merged into one screen (10 Aug 2026)** — five merchant screens, not six, and `/merchant/[handle]/profile` survives as a redirect. Settings was a read-only echo: its four rows (payout, handle, category, registered) were each rendered better elsewhere — payout on Payouts with the rotation rule and a Basescan link, and again in the sidebar footer; handle and category as the locked fields on the profile form, beside the reason each is locked; the registration date in the payer preview. Its only original content was the chime toggle and three Basescan links. The rows were **deleted, not moved**: a fourth rendering of the same on-chain facts is not what a merchant was missing. The surviving screen keeps the name **Settings** rather than Shop profile — the same test the Overview/Settlements rename used (label by what is behind it), and "Shop profile" would be actively wrong for the chime and the contracts, whereas "Settings" is merely generic for one section that carries its own "Shop profile" label inside it.
- **The merchant shell mounts a `ToastProvider`, and a successful profile save is a TOAST while a failed one stays inline.** That asymmetry is the rule, not a preference: a toast is unreadable to anyone who looked away, so a success may be transient and a failure may not. The inline "Saved." it replaced sat above a button that the save itself had just disabled — the least-looked-at spot on the screen at that moment. **The merchant viewport must be `fixed`, not the default `absolute`**: the payer app can anchor to its own frame because that frame is `h-dvh overflow-hidden`, but the merchant column is a stretched grid item in document flow, so `bottom-0` would mean the bottom of a page that scrolls well past the viewport — a confirmation below the fold, on the one screen that no longer has any other. `cn` is tailwind-merge, so passing `fixed` in `viewportClassName` wins.
- Scope decisions taken, recorded so they are not re-opened by accident: **no merchant directory** (a payer reaches a shop from a receipt or from their own history — a directory implies a curation we do not do); **no logo upload** (a deterministic tile from the handle; no blob storage); the **Payouts** screen ships the payout-address card and the "there is no payout schedule — each payment settles to your address in the same transaction" framing, with only the per-day breakdown pending; **merchant category is not editable**, because `GantryCore` has no setter for it and a form that silently fails to write the chain is worse than no form.
- Copy correction applied everywhere: **"Registered on-chain", never "Verified on-chain"** — registration is permissionless and self-attested, and "verified" implies a KYC that does not exist.

## Status: one chain of record, one deploy block, no reset (11 Aug 2026)

The whole rail was redeployed as a unit so that **the chain is the source of every displayed row that can come from a chain**. Driven by a single question — why do the demo laptop and the deployed host disagree? — and the answer was structural: one table held facts the chain could not re-supply, and two contracts had two deploy blocks. Tests: **180 forge** (175 + 5 skipped fork), **110 shared**, **119 backend**. These are the current numbers and the deck quotes them.

**Live contracts — all four Basescan-verified, deployed in ONE run at block 45307715:**

| Contract | Base Sepolia address |
|---|---|
| GantryCore | `0xd9A2F4A97d119d0dE6bfb90A2Ba2a601675F3e61` |
| FixedRateSwap | `0x2590C808C08819Fa47129e02bE3460d3165Ad14c` |
| MockXSGD | `0xDD922ede4103467449B3626Ff97b674c84761ab7` |
| AgentPBMWalletFactory | `0x7E864606d6c86Fa1d7d6B1c7faE8CE555164a21a` |
| **`BASE_SEPOLIA_DEPLOY_BLOCK`** | **45307715** — one constant, serving the sweep AND the wallet lookup |

**The merchant record is on-chain.** `Merchant` carries `displayName`/`location`/`blurb`; `registerMerchant` takes all six fields (so onboarding still costs one transaction) and `setMerchantProfile` is `onlyRelayer` and provably cannot touch payout, handle or category — an operator who can rename a shop must not be able to redirect its money. A `MerchantProfileUpdated` event fires on both register and update, so an indexer follows **one** event for current text. The on-chain bound is **4× the clients' codepoint limits** (240/320/560 bytes vs 60/80/140 codepoints): a UTF-8 codepoint is at most 4 bytes, so anything `normalizeProfile` accepts always fits and the client rule stays the binding one — the byte-vs-codepoint drift trap the agent `label` documents, avoided by arithmetic instead of by care.

**Moving it on-chain removed the only chokepoint that enforced `normalizeProfile`** — `registerMerchant` is permissionless and the contract checks length only, so an RLO override, a newline or zero-width padding would render everywhere, and `" "` is truthy so the handle fallback never fired. The chokepoint moved to the READ path: `resolveProfile` trims and drops deceptive text, pinned by a test. Any new writer of merchant text inherits this — validate on read, because you do not control who calls the contract.

**`WalletCreated` is swept by the indexer**, one `getLogs` over both addresses (they share a deploy block, so no range exists where only one can have logs). That deleted ~470 lines: `runRanges`, the retry backoff, `scanCursor`, the deadline and the concurrency tuning — the code that actually failed on Render's shared egress IP. Wallets land in `agent_wallets`, and lookups are `walletsOf(owner)` (one `eth_call`, always current — what the payer app needs right after creating a wallet) plus the swept table for signer lookups. **A failed sweep must never answer "you have no agents" with a 200**: `candidates()` raises 503 `AgentIndexUnavailable`, because an empty list is what makes an agent CLI mint a duplicate wallet. `sweepNow()` waits a running pass out and starts a fresh one — joining an in-flight pass returns a sweep whose head was read before the caller arrived, i.e. blind to exactly the wallet being asked about.

**`agent_wallets` rows carry their factory** and every read filters on the current one. A row from a retired factory is the dangerous kind of stale: the wallet answers `owner()`/`policy()` perfectly so it lists as healthy, while its immutable `CORE` is the dead core and every payment through it reverts. Unknown-provenance rows (pre-migration) default to matching nothing rather than being trusted.

**THERE IS NO RESET. Nothing clears rows, hides rows, or rewinds the cursor** — and this is the load-bearing half of the change, so do not reintroduce it under any name.

`clearCache`, the cursor jump, `resetEpoch`, `resetIndexer`, `POST /api/admin/reset`, the SSE `reset` event and its listener in `use-merchant-feed` are all deleted. So is the display floor that briefly replaced them (built and removed the same day). **Every one of those was per-host state, and per-host state is exactly what makes a demo laptop and the deployed backend show different books while indexing the same chain from the same block.** A floor was better than a delete — it destroyed nothing — but it did not fix the disparity, because the two hosts still *rendered* different sets. Nothing can: emptiness on one host and history on the other is a contradiction, not an implementation problem.

So the rule is: **every host sweeps forward from `BASE_SEPOLIA_DEPLOY_BLOCK` and shows everything it finds.** Two hosts at the same cursor hold and display the same *swept* rows, checkable by comparing `/api/settlements?limit=1` totals.

**Two tables are NOT swept, and pretending otherwise is the error to avoid.** `denials` exists because a policy revert is caught by simulate-before-send and never broadcast — there is no event and no log, so that row is the only trace anywhere, and it lives only on the host that refused the payment. `intents` is backend-written too (`IntentCreated` is deliberately not in `SWEPT_EVENTS`). So `/api/denials` legitimately differs between a laptop that ran the rejection beat and a host that did not, a fresh Render disk comes up with no denials and never refills them, and the settlements-total check above is blind to all of it. That is the one remaining place two backends of the same chain disagree, and it is a real gap rather than an unfinished feature — see the honest-labels list.

**A clean book is a fresh core.** `pnpm contracts:fresh` deploys all four contracts together, pins a new `BASE_SEPOLIA_DEPLOY_BLOCK`, and drops the local database; every host then backfills from that block and they start equal *and stay equal*. That is the whole rehearsal-reset story now: if the book must be empty for a run, deploy. It costs a few minutes and a Vercel rebuild, which is the honest price of a property that holds everywhere rather than on one laptop.

Consequences: `demo:reset` no longer touches the feed (it provisions money, merchants and policy — the name is legacy); `intents` and `denials` are never truncated and grow slowly on a long-lived box; and `/health` carries no "what am I showing" field, because there is nothing left for one to explain.

**`agentPayer` went the same way, and for the same reason** (11 Aug 2026). A bridged x402 `exact` payment hops agent → relayer → core, so the on-chain payer is the RELAYER and the buyer's own address appears nowhere on-chain — only the backend that performed the hop ever knew it, and it wrote that into its own SQLite. So the field was populated on one host and null on every other, and lost on any rebuild: the same "fact the chain cannot re-supply" class as `merchant_profiles`, and the last thing making two backends of the same chain disagree about a settlement. It is replaced by a DERIVED `SettlementEvent.bridged` — `door === "agent" && payer === relayer`, both from the event — computed server-side where the relayer address already lives. Nothing else produces that pair: `settleFromPBM`'s payer is the wallet contract, and a nonce-pinning `exact` client's payer is the agent itself. The UI shows "via facilitator" instead of the burner address, which is information we only ever had half the time; the x402 `PAYMENT-RESPONSE` still reports the real payer, taken from the authorization in hand rather than from storage.

**`pnpm contracts:fresh` is the redeploy, and it is not `demo:reset`.** Run by hand, rarely: it sweeps USDC out of every wallet the redeploy will orphan (live factory *and* `BASE_SEPOLIA_RETIRED_FACTORIES`, and it appends the outgoing factory as it repoints the table, because that blind spot is silent and permanent), runs `DeployAll`, reads the broadcast receipts, and rewrites `addresses.ts` in place — matching contracts by **name**, never by receipt position, so reordering the deploys cannot silently swap two valid-looking addresses. Every precondition (`forge` and `cast` runnable, deploy key present, **deployer === the backend's relayer** or the new core's `onlyRelayer` is wrong forever, Etherscan key) runs *before* anything irreversible. Verification uses `verify-contract` per address, not `forge script --resume --verify`, which demands an unlocked wallet for transactions already mined. `demo:reset` must never redeploy: it has a 30s budget, and rewriting `addresses.ts` would leave the Vercel build (which inlines it) pointing at dead contracts.

**After any redeploy: `pnpm abis`, commit, and rebuild BOTH hosts** — Next inlines addresses at build time, so an un-rebuilt Vercel deployment silently follows a dead contract.

`NEXT_PUBLIC_BACKEND_URL` was missing from the FIRST Vercel build and was fixed the same day; the shipped bundle now carries `onrender.com` and no `localhost:4000`. Keep the failure shape, because it is silent in a way that wastes an afternoon: an unset var falls back to `http://localhost:4000` (`web/src/lib/env.ts`), so every screen fetches the *visitor's own* machine. Chrome 138+ gates a public origin reaching localhost behind the Local Network Access permission, so the visitor sees an "Access other apps and services on this device" prompt and then "Can't reach the backend / Failed to fetch" whichever button they press. `NEXT_PUBLIC_*` is inlined at build time, so the fix is always **set it and redeploy** — saving it alone changes nothing. **Verify by grepping the built chunks for `onrender.com`, never by reloading the page**, and note the same trap has no fingerprint for `NEXT_PUBLIC_DEMO_KEY`, whose fallback is `undefined`; that one can only be confirmed in the Vercel dashboard.

**Web → Vercel** (import the repo, Root Directory `packages/web`; Vercel detects Next.js). The only committed Vercel config is `packages/web/vercel.json`, and it does exactly one thing — an `installCommand` of `pnpm install --frozen-lockfile --filter @gantry/web...` so the build installs the web package and its workspace deps rather than the whole monorepo. The Dockerfile, `.dockerignore` and root `vercel.json` committed on 8 Aug were **reverted the same day** and stay reverted: Render's native Node deploy needs no container. **Backend → Render free web service** (`pnpm install --frozen-lockfile` / `pnpm --filter @gantry/backend start`, no container).

**The backend cannot be serverless**, and SSE is only the visible half of why: the relayer's nonce counter, the faucet's two legs (a per-address cooldown, an in-flight set and a rolling daily ceiling EACH), the merchant-registration and profile-edit cooldowns, the registration-date map and the factory `WalletCreated` cache are all in-process, and the indexer holds a WS subscription plus a 15s `setInterval` sweep. It must run as **exactly one instance, never autoscaled** — two would claim the same nonce and halve every rate limit. A persistent disk is NOT needed for the settlement feed — the sweep rebuilds `settlements` and `agent_wallets`, so a wiped disk costs a cold backfill. It DOES cost the two backend-written tables: `denials` most of all, since a refused agent payment has no event to re-sweep and the row is its only record. A cursor-less indexer re-sweeps from the deploy block in 1,999-block chunks (growing ~43k blocks/day, i.e. ~22 chunks a day; the 11 Aug redeploy reset that floor to block 45307715) — and every one of those chunks is refused by the paid Alchemy endpoint (free tier: **ten** blocks) and served by the public node, so a cold start leans on the rate-limited provider, not the paid one.

**`GET /health` is the host's health-check path, and nothing on it may leave the box** (9 Aug 2026). It returns `{ok, timestamp, uptime, hostClass, chainId, relayer, indexer:{cursor, head, lag, headAt}}` at the cost of one local SQLite read, and makes no RPC call: the host polls this path and restarts the service when it fails, so an awaited `getBlockNumber()` (what it used to do) handed a provider the power to kill an instance mid-sweep. There is deliberately no per-host "what am I showing" field: two hosts at the same `cursor` show the same rows, so `cursor` is the whole answer. The chain facts come from module state the indexer's 15s sweep already records, which is also the better signal: a stale `headAt` means the RPC path is failing, while a growing `lag` means the reads work and the `getLogs` chunks do not. `ok` is liveness only and never folds in a chain verdict. Two fields exist for the deployed host specifically: `uptime` answers "did I just pay a cold start", and `hostClass` is the only way to confirm `NODE_ENV=production` landed once the boot warning has scrolled away — `classifyHost` fails OPEN on a typo.

**The deployed instance is a shop window, not the demo** — the stage run is on the laptop, because payer funding and self-service onboarding only work on a demo host. Render's free-tier spin-down (~50s cold start) therefore costs a browsing screener, not the demo. On the host set `NODE_ENV=production` (caps both faucet legs, closes self-service onboarding, closes unauthenticated profile edits) and `CORS_ORIGIN`. **The Vercel build additionally needs `NEXT_PUBLIC_DEMO_KEY=0x<key>`, `NEXT_PUBLIC_APP_URL`, `NEXT_PUBLIC_BACKEND_URL` and `NEXT_PUBLIC_WALLETCONNECT_PROJECT_ID` set BEFORE the build** (inlined, not runtime-read, so a missing one cannot be fixed without redeploying). Without the demo key the deployed payer page serves only connected wallets, and the whole reason the faucet is capped rather than switched off evaporates. **Understand what that key is before setting it:** `NEXT_PUBLIC_*` is inlined into the client bundle, so it is readable by anyone who opens devtools, and it is a *shared* account — every visitor to the deployed build signs as the same payer and sees the same payment history. That is acceptable only for a demo account holding testnet funds, it belongs on the honest-labels list, and it must never be the relayer's key. The deployed instance must hold the SAME relayer key as the laptop — `GantryCore` stores one `onlyRelayer` address, so a different key cannot create intents. `.github/workflows/ci.yml` (lint, typecheck, both node suites, `forge test`) is kept.

Say "Registered on-chain", never "Verified on-chain": registration is permissionless and there is no KYC.

Say **self-attested**, and never "verified". ## Conventions

- pnpm workspaces monorepo. TypeScript everywhere outside `packages/contracts`.
- Everything on `main`, incremental focused commits, Conventional Commits (`feat(contracts): …`). No AI co-author trailers.
- Verify with `pnpm lint` + `tsc --noEmit` (and `forge test` for contracts), not full builds.
- **`e2e:pbm` lives in `packages/agent`, not the backend** — it is `pnpm --filter @gantry/agent e2e:pbm`. Its two siblings (`e2e:pay`, `x402:buy`) are `@gantry/backend`. Naming the wrong package has already sent someone looking in the wrong place; always write the filter out in full.
- **Milestone review gate:** before declaring any milestone (M0–M4) done, run the PR review skill (`pr-review-toolkit:review-pr`) over the milestone's full commit range (e.g. `git diff <last-milestone-tag-or-commit>..HEAD`), triage findings with the user, and fix agreed ones before sign-off. Same applies to any large multi-commit change outside milestones.
- **The repo is PRIVATE** (checked 8 Aug 2026) despite the original "public from day 1" plan. The submission package lists a *public* GitHub repo as one of its five artifacts, so this must flip before submitting or screeners get a 404 — and the Gemini key (which transited a chat) must be rotated BEFORE it flips, not after. Commit history is feasibility evidence for screeners; keep `.env.example` current.
- Demo-script-driven development: if it doesn't appear in the demo script or submission materials, don't build it.
