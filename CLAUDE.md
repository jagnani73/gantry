# Gantry — Project Guide

Hackathon project for NTU InnovateX 2026 (Track 1: Payments & Financial Infrastructure). Solo builder (NTU student, Student Group entry). This file is the canonical context for working sessions — read it fully before building.

## What Gantry is

A payer-agnostic payment rail on stablecoins. One on-chain `PaymentIntent`, one settlement contract, two doors:

- **Human door:** printed static QR encodes `…/pay/<handle>` → mobile payer page → payer signs an EIP-3009 `transferWithAuthorization` (gasless — tourist needs zero ETH) → relayer settles.
- **Agent door:** HTTP `402 Payment Required` with x402 v2 `PAYMENT-REQUIRED` header; `accepts[]` offers the standard `exact` scheme (any vanilla x402 client can pay) AND a custom `gantry-pbm` scheme (agent session key EIP-712 sig, executed through an on-chain policy wallet).

Both settle through `GantryCore._settle()`: pull funds → swap to XSGD if needed (min-out guard) → pay merchant → emit `IntentSettled`. Merchant dashboard shows both payer types landing in one live feed. That convergence IS the thesis — never build anything that exists for only one door except the thin encoding layers.

**Pitch line:** "x402 standardized how machines pay. Gantry is the rail that lets one merchant accept payments from machines and humans alike."

**Framing is strictly Singapore-centric:** XSGD settlement, hawker/tourist scenes, PayNow's structural gaps (no foreign payers, no agent payers), PBM framing after MAS Project Orchid.

## Architecture (decided — do not relitigate without user)

**Contracts** (`packages/contracts`, Foundry, Solidity ^0.8.24, OZ only for ERC-20/Ownable). **OpenZeppelin comes from npm** (`package.json`, pinned exact to 5.7.0), not `forge install` — OZ's own docs warn a git install can silently follow the unreleased `master` on update, while a published npm version is immutable. Remappings live in **`remappings.txt`, which shadows any CONFLICTING prefix in `foundry.toml`** — a prefix defined only in `foundry.toml` still applies, but one defined in both resolves from `remappings.txt`, so put mappings there to avoid guessing (verified in a scratch project). `forge-std` stays a submodule (test-only, no npm distribution), so a fresh clone needs `git submodule update --init`. (`--recursive` used to be actively harmful because it pulled OZ's own test submodules; now that OZ is an npm dependency it is merely a no-op, since forge-std has no submodules of its own.) Switching the OZ path changed no executable code (proven: identical source under both layouts with metadata disabled builds byte-identically) but did change the embedded metadata hash, so a fresh build no longer byte-reproduces the deployed bytecode; the on-chain contracts and their Basescan verification are unaffected:
- `GantryCore.sol` — merchant registry (`registerMerchant(handle, payout, categoryId)` = the 2-min onboarding, plus `setMerchantPayout` rotation gated on the current payout), `PaymentIntent` lifecycle, `settleWithAuthorization()` (QR + x402 `exact`; **EIP-3009 `nonce` must equal `intentId`** — binds signature to intent) and `settleFromPBM()` (Agent-door intents only); shared `_settle` with reentrancy guard, 0.5% protocol fee skim (`feeBps=50`, capped 2%); custom errors; `IntentSettled(intentId, merchantId, payer, tokenIn, amountIn, xsgdOut, feeXsgd, door)` — xsgdOut is gross, merchant receives xsgdOut − feeXsgd. Ownable2Step, renounce disabled.
- `AgentPBMWallet.sol` + factory — `owner` (human) funds it and sets `Policy {dailyCap, perTxCap, expiry, categoryBitmap}`; `agentSigner` is the agent's session key. `authorizeSpend()` (onlyCore) verifies EIP-712 sig + all policy dimensions + daily window. Custom errors `PerTxCapExceeded`, `DailyCapExceeded`, `CategoryNotAllowed(uint16)`, `PolicyExpired` — these exact names surface in the demo; facilitator returns them as x402 `invalidReason`.
- `FixedRateSwap.sol` (owner-set rate, seeded 1.3421) behind the `IGantrySwap` interface — this is what ships. **`GantrySwap.sol` (x·y=k AMM) is SKIPPED by decision (7 Aug 2026)**: do not build, deploy, or wire an AMM unless the user explicitly asks. The seam is the point — production FX means real XSGD liquidity via aggregator/RFQ behind the same interface, not a toy pool. Label the demo rate as owner-set everywhere.
- `MockXSGD.sol` (and `MockUSDC.sol`, now deployed-but-unused — the app moved to real Circle USDC on 7 Aug 2026; **removed from `addresses.ts` and from every deploy script's minting on 8 Aug 2026**, it survives only as the Foundry suite's generic EIP-3009 test double and as the historical address in the table below) — both extend a shared hand-written `EIP3009` base (FiatToken-shaped: typehashes, `authorizationState`, events), 6 decimals, open mint. XSGD carries EIP-3009 deliberately: real XSGD supports x402 natively (StraitsX), and XSGD-direct settlement flows through the same authorization door. XSGD exists on NO testnet — mock is the honest option; label it.
- Primary pay token on Sepolia: Circle's real testnet USDC `0x036CbD53842c5426634e7929541eC2318f3dCF7e` (implements EIP-3009, has faucet). Fork-test against it from the start — EIP-3009 domain/sig quirks are a known risk.

**Backend** (`packages/backend`, Node 22 + Express + viem): merchant API; x402-protected routes via `@x402/express` pointed at our own facilitator; facilitator `/verify` + `/settle` (spec-shaped, `@x402/core` types, hand-rolled `gantry-pbm` handler); relayer (holds the only gas key — payers never send transactions); SSE indexer via `watchContractEvent` over WebSocket RPC; paged read surface for the two UI surfaces (`GET /api/settlements`, `/api/denials`, `/api/agents`). **Brand mark** (added 9 Aug 2026): a portal frame with two ramps running out from under it — the two doors converging on one rail. It is drawn in the existing tokens (ink, accent, accent-tint), so it was adopted as-is rather than recoloured. ## Canonical demo facts (bake into seed data / `demo-reset` script)

- Merchant: **"Ah Hock Chicken Rice"**, Maxwell Food Centre, category `food_beverage`.
- Human payment: **iced tea S$1.50** → 1.117652 USDC → 1.50 MockXSGD @ 1.3421.
- Agent payment: **3 iced teas for the team = S$4.50** (3.352955 USDC).
- Prices are hawker-drink scale on purpose: settlement is in REAL Circle USDC now, which is finite, and S$1.50 is a real drink price so the Singapore framing survives. A full run costs ~4.5 USDC.
- Agent policy: S$50/day cap, categories `[food_beverage]`, 30-day expiry, revocable.
- Rejection beat: "GadgetHub SG" (`electronics`), **S$4 phone cable** → on-chain revert `CategoryNotAllowed`. Cheap on purpose: it is *inside* every cap the wallet has, so the only thing that can stop it is the category — "the amount was fine, the category wasn't". It also has to be affordable, because the facilitator's balance pre-check runs BEFORE the on-chain policy check: price it above the wallet's balance and the beat dies as `insufficient_funds`, which is the wrong story entirely (this is why `demo-reset` tops the wallet to 10 USDC).
- Fee story: on the day's **S$6.00**, Gantry takes **S$0.03** and cards would take **S$0.168**. Narrate it as a rate against real volume, not a day's total — "three cents on six dollars; a hawker doing S$2,000 a month pays S$10 with us and S$56 with cards". **Trap:** the Overview screen's **Saved vs cards** tile renders **S$0.13**, which was the OLD number for Gantry's cut — do not say "we took thirteen". The three tiles are *Collected, last 7 days* (net, **S$5.97** on demo day), *Paid by* (an agent/human split bar over payment COUNTS, not money) and *Saved vs cards* (**S$0.13** = card fee − our fee, clamped at zero); the gross and the card fee are never on screen. **The tiles cover a ROLLING 7-day window, not a day and not a calendar week** (changed 10 Aug 2026): `OVERVIEW_WINDOW_DAYS` in `feed-state.ts`, start day from `minusDaysKey`, pinned to SGT. Rolling specifically because a calendar week empties itself at its own boundary — on a Monday morning "this week" reads zero though the shop traded all weekend, and a merchant cannot tell that from a dead feed. Demo figures are unaffected, since every payment in a run lands the same day. Two consequences: the "loaded so far" partial warning now fires routinely (7 days hold ~7× the rows one page carries, so **the "Load older" button beside it is load-bearing, not an edge case** — it fires whenever a full 50-row page fits inside the window, which is the normal case on the demo book), and the sidebar's Overview count is the window's.
- **Merchant display facts are ON-CHAIN** (since 11 Aug 2026). `GantryCore.Merchant` carries `displayName`, `location` and `blurb` beside handle/payout/category; there is no `merchant_profiles` table and no seed fallback anywhere — an absent field renders as nothing rather than as an invented name. `demo-reset` registers the canonical shops from `DEMO_MERCHANTS` in `packages/shared/src/constants.ts`, which is now the *input to a chain write* rather than a table the backend fell back to; `DEMO_MERCHANT_HANDLE` is the one shop every handle-less link falls back to.
- `demo-reset` = one command, Sepolia-based: top up the funder, fund the demo payer, register the canonical shops on-chain, provision/top up and re-arm the demo agent, check gadgethub-sg is registered; contracts persist and the relayer holds gas ETH. It waits on real receipts (the "<1s" figure predates M3) and must stay **<30s**: that budget is what enables rehearsal. **It does not touch the transaction feed and cannot** (11 Aug 2026) — the name is legacy; it provisions money, merchants and policy, nothing else. **A clean book is a fresh core, `pnpm contracts:fresh`.** **The re-arm is signed by the demo PAYER's key, not the relayer's** — `setPolicy` is `onlyOwner` and agent wallets are payer-owned, so nothing on the server can arm a policy any more. **The 30s register cooldown is in-process and survives `demo-reset`** — back-to-back onboarding takes inside 30s will 429; restart the backend between them. Redeploying contracts is a DIFFERENT script, `pnpm contracts:fresh`, run by hand and never before a demo.

The x402 agent door is live end-to-end on Base Sepolia: `POST /api/order/:handle?sgd=…` 402-challenges with a spec-shaped v2 `PAYMENT-REQUIRED`, an **unmodified vanilla `@x402/fetch` client pays it** (the interop beat), and the settlement lands in the same dashboard feed as QR payments with the Agent badge. **The load-bearing M2 discovery:** vanilla x402 v2 `exact` clients random-generate the EIP-3009 nonce (`createNonce()` in `@x402/evm`; no pinning extension), but the frozen core hardcodes `nonce = intentId`. On-chain payer is the relayer (one custodial hop, PSP-style — on the honest-labels list); the agent's address travels in `PAYMENT-RESPONSE`. *(It also rode SSE rows as `agentPayer` until 11 Aug 2026 — that field is gone; rows now carry a derived `bridged` boolean and the UI says “via facilitator” without an address. - **Trust channel:** the bridge's order facts (`handle`, `xsgdAmount`) come ONLY from server-pinned `requirements.extra` (the SDK subset-matches extra against the client echo; the client-echoed `resource.url` is never load-bearing — a client could echo another merchant's URL at the same price). Design notes that bind later work:
- **`agentStatus()` is the only correct way to badge a policy** — tri-state `active | lapsed | revoked`. `revoked` is derived from `expiry === 0`, so a *naturally lapsed* policy (`0 < expiry < now`) denies every spend while `revoked` stays false; re-deriving the badge by hand renders a dead policy as "Active". The comparison is pinned to `authorizeSpend`, which reverts when `block.timestamp > expiry` — so `expiry` is the LAST second a spend is allowed and `now === expiry` is still active. Pass chain time when you have it: a laptop minutes fast would badge a working policy "lapsed".
- **The agent daily window rolls at `block.timestamp / 1 days` — UTC days, i.e. 08:00 SGT**, not local midnight. Any copy explaining the cap must say "resets 08:00 SGT".
- **Never hand viem a bare address as an explicit `account` on a client that signs locally** (found 10 Aug 2026, and it had broken every browser-signed owner write since payer-owned agents landed). An explicit `account` OVERRIDES `client.account`, and `parseAccount` reads a string as a **json-rpc** account — the signal for "the node holds this key" — so `writeContract` called `eth_sendTransaction` against a plain HTTP transport and `sepolia.base.org` answered `unknown account`. `simulateContract` only reads `.address`, so simulations pass and the failure looks like an RPC fault. `agent-writes.ts` therefore returns the CLIENT and no separate account, and every call site passes `client.account`. Nothing in the sign-off gate covers this: `demo-reset.mjs` had the correct pattern all along, so it proves the demo KEY can arm a policy, never that the browser can. **The manual browser pass is now: create agent → arm → rotate the session key → revoke → withdraw, plus rotate a merchant payout from a connected wallet.** That last one is the newest and the least exercised — it is the only merchant-side browser write in the app, it is gated on `msg.sender == merchant.payout` so it cannot be rehearsed with the demo key, and it has never run against a live core.
- **`waitForTransactionReceipt` without `onReplaced` silently resolves with a DIFFERENT transaction's receipt** — it scans for one with the same `from` and `nonce` and returns that. On the shared demo key, where every visitor of a deployed build signs as one account, that is a routine collision rather than an exotic one: it would grade a stranger's transaction as our success, and `createWallet` would parse the stranger's logs and hand back their wallet address. Every browser wait passes `onReplaced` and raises `UnknownOutcomeError` — unknown, never failed, because ours never mined.
- **A write the payer signs is confirmed against a DIFFERENT provider than the read that follows it** (10 Aug 2026). The browser waits for its own receipt on its own RPC; every screen then re-reads through the backend, which uses its own fallback chain — so a read issued milliseconds later is routinely served by a replica without the block, and the payer is returned to a screen still showing the rules they just changed, which is indistinguishable from the write doing nothing. The browser holds a mined receipt for the policy it sent, so any read that disagrees is behind: `policyFingerprint` (everything an owner write can change — the four policy fields plus `label` and `agentSigner` — never `spentToday` or the balance, which move on their own) is recorded through `expectAgentPolicy` and the detail screen re-reads on a bounded poll until it matches. Same discipline as the payer store's balance watch. It applies to **revoke** too, where a stale read leaves a chip saying "Active" over a wallet that now reverts everything. **Known-superseded data is not rendered at all** while that wait runs — the detail screen falls back to the store's agent list when its own read has not landed, so without the gate the first paint after a save is the OLD policy, which then silently becomes the new one under the payer. A frame that states the wrong caps is a claim about the chain, and a brief "Your change is on-chain. Reading it back…" is the honest version of the same second.
- **An agent's name and its policy date are ON-CHAIN, and the factory was redeployed for them (10 Aug 2026).** `AgentPBMWallet` gained `string label` (owner-set, taken by `createWallet` so naming costs no transaction of its own) and `uint40 policyUpdatedAt` (written by the one internal path `setPolicy` and `revoke` share, so a revoked wallet dates from its revoke). `policyUpdatedAt` packs beside `_lastSpendDay`/`_spentToday` — 64+128+40 bits, slot 7 offset 24, verified with `forge inspect AgentPBMWallet storage-layout` — so `_setPolicy` still writes the day bucket, the counter and the stamp in one SSTORE. It is out of the `Policy` struct **for the calldata, not for the storage**: a member there rides in `setPolicy(Policy calldata)` as a caller-supplied field the contract immediately overwrites. (Storage was not the reason, and an earlier version of this note wrongly said it was — `expiry`'s slot has 27 spare bytes because `categoryBitmap` needs a whole slot regardless, so a `uint40` inside the struct would also have been free. A reader "optimising" on the false premise would move the field and reintroduce the calldata wart.) Both replaced worse answers: the label was a localStorage map, invisible on any other device and so doubly wrong on a build where every visitor shares one demo key; the date was a bounded backwards log scan that could not answer for a policy older than the window it searched. **The field is `label`, never `name`** — `DOMAIN_SEPARATOR()` hashes the literal `"AgentPBMWallet"`, and a `name()` getter beside it invites wiring the two together, which would kill every agent signature the moment an owner renamed. **31 BYTES, not characters** (`bytes(label).length`, the inline-string bound): eight 4-byte emoji are already over, so a client counter that measures codepoints — as `profileFieldLength` deliberately does for merchants — would offer a label the contract refuses. Renaming an existing wallet is its OWN transaction: `setPolicy` must not carry it, because that call resets the daily counter and a rename must never cost the agent its budget. A redeploy orphans every wallet the previous factory made — they still work, nothing lists them — which is accepted whenever the wallet ABI changes, since a factory can only mint what it was compiled against. Reads of the two new getters degrade to `""`/`0` rather than marking a wallet unreadable, so an old wallet's policy can still be read and revoked.
- **A mined deploy is proof, and a visibility poll after it is best-effort.** `AgentPBMWalletFactory.createWallet` has no idempotency — it pushes a fresh wallet on every call — so a throw after the receipt drops an address that exists on-chain, and the caller's retry mints a SECOND wallet for the same signer. Return the address even when the follow-up read cannot see it yet.
- **A denied payment has no reverted transaction.** The revert is caught by simulate-before-send and never broadcast, so the only hashes that exist are the intent-creation tx and the cancel tx — and since 11 Aug 2026 that cancel is also what CARRIES the reason on-chain (`cancelIntentWithReason` → `IntentDenied`). A declined receipt reads "Cancelled · 0x…" from `cancelTxHash` and "Moved: Nothing"; when the cancel itself failed, render no hash at all rather than inventing one. The error name travels **verbatim** (`CategoryNotAllowed`) — the UI may explain it alongside, never instead of.
- **`payer` on `/api/settlements` is a comma-separated list, matched against the on-chain `payer`.** A PBM payment's on-chain payer is the wallet, not the human, so the payer app passes its own address AND its wallets — filtering on the human's alone would hide exactly the rows the agents screen exists to show. *(It also matched an `agentPayer` until 11 Aug 2026; that column is gone — see `SettlementEvent.bridged` in the 11 Aug section. A bridged row's on-chain payer is the relayer, so it is nobody's row, on every host equally.)*
- **Alchemy's free tier caps `eth_getLogs` at TEN blocks** (measured 8–9 Aug 2026; an earlier comment claimed 10k). Every 1,999-block sweep chunk is therefore rejected by the paid primary and served by `sepolia.base.org` — two RPC calls per chunk, and **the rate-limited public node is what actually carries the correctness path**. Raising the chunk wedges the sweep entirely (the cursor never advances); dropping it to 10 turns a cold backfill into thousands of calls. The constant now has exactly ONE consumer, the indexer sweep: the factory scan in `services/agents.ts` was folded into it on 11 Aug 2026 and the registration-date scan in `services/merchants.ts` went the same way with the directory. Both deletions were the same trade — a second walk over a range the sweep already covers, for facts the sweep can carry for free.
- **An RPC rate limit belongs to the EGRESS IP, not to the endpoint** (measured 9 Aug 2026, after the deploy). The factory scan in `services/agents.ts` — 54 chunks at concurrency 4 — completes against `sepolia.base.org` from a laptop with zero failures in ~5.7s, and dies on Render after ~48 chunks in 1.8s with "over rate limit" from that same endpoint. So any concurrency constant tuned on the laptop is a throughput choice and never a safety mechanism, and "swap to a better provider" is unfalsifiable from here: publicnode and tenderly also passed cleanly from the laptop, which proves nothing about Render's shared IP. What actually holds is `runRanges` + `RETRY_BACKOFF_MS` (retry ONLY the failed chunks, 750/1500/3000ms, whole scan idle through the wait — viem's own 3× 150/300/600ms retry loses because it backs off while the rest of the batch keeps firing, which is exactly when a token bucket cannot refill) and `scanCursor` in agents-core (a partial scan keeps the ground it covered, so a retry finishes the tail). Without that cursor the failure is self-sustaining: a throttled scan discarded every chunk that succeeded, and the payer's retry re-fired all 54 into an empty bucket — a page that should be slow was permanently broken instead. **The remaining structural fix is to fold `WalletCreated` into the indexer's persisted sweep** (`getLogs` takes an address array, so both contracts cost the calls the indexer already makes): the agents scan currently re-walks the same block span the indexer already walks, and it grows ~22 chunks/day — ~310 chunks per cold process by the finals, on a free tier that spins down so most visits are cold.

**The merchant record is on-chain.** `Merchant` carries `displayName`/`location`/`blurb`; `registerMerchant` takes all six fields (so onboarding still costs one transaction) and `setMerchantProfile` is `onlyRelayer` and provably cannot touch payout, handle or category — an operator who can rename a shop must not be able to redirect its money. A `MerchantProfileUpdated` event fires on both register and update, so an indexer follows **one** event for current text. The on-chain bound is **4× the clients' codepoint limits** (240/320/560 bytes vs 60/80/140 codepoints): a UTF-8 codepoint is at most 4 bytes, so anything `normalizeProfile` accepts always fits and the client rule stays the binding one — the byte-vs-codepoint drift trap the agent `label` documents, avoided by arithmetic instead of by care.

**Moving it on-chain removed the only chokepoint that enforced `normalizeProfile`** — `registerMerchant` is permissionless and the contract checks length only, so an RLO override, a newline or zero-width padding would render everywhere, and `" "` is truthy so the handle fallback never fired. The chokepoint moved to the READ path: `resolveProfile` trims and drops deceptive text, pinned by a test. Any new writer of merchant text inherits this — validate on read, because you do not control who calls the contract.

**`WalletCreated` is swept by the indexer**, one `getLogs` over both addresses (they share a deploy block, so no range exists where only one can have logs). That deleted ~470 lines: `runRanges`, the retry backoff, `scanCursor`, the deadline and the concurrency tuning — the code that actually failed on Render's shared egress IP. Wallets land in `agent_wallets`, and lookups are `walletsOf(owner)` (one `eth_call`, always current — what the payer app needs right after creating a wallet) plus the swept table for signer lookups. **A failed sweep must never answer "you have no agents" with a 200**: `candidates()` raises 503 `AgentIndexUnavailable`, because an empty list is what makes an agent CLI mint a duplicate wallet. `sweepNow()` waits a running pass out and starts a fresh one — joining an in-flight pass returns a sweep whose head was read before the caller arrived, i.e. blind to exactly the wallet being asked about.

*(`WalletCreated` was joined by `MerchantRegistered` and `MerchantProfileUpdated` on 11 Aug 2026, on exactly this argument — see the directory section below. `SWEPT_EVENTS` is 6.)*

**`agent_wallets` rows carry their factory** and every read filters on the current one. A row from a retired factory is the dangerous kind of stale: the wallet answers `owner()`/`policy()` perfectly so it lists as healthy, while its immutable `CORE` is the dead core and every payment through it reverts. Unknown-provenance rows (pre-migration) default to matching nothing rather than being trusted.

**THERE IS NO RESET. Nothing clears rows, hides rows, or rewinds the cursor** — and this is the load-bearing half of the change, so do not reintroduce it under any name.

`clearCache`, the cursor jump, `resetEpoch`, `resetIndexer`, `POST /api/admin/reset`, the SSE `reset` event and its listener in `use-merchant-feed` are all deleted. So is the display floor that briefly replaced them (built and removed the same day). **Every one of those was per-host state, and per-host state is exactly what makes a demo laptop and the deployed backend show different books while indexing the same chain from the same block.** A floor was better than a delete — it destroyed nothing — but it did not fix the disparity, because the two hosts still *rendered* different sets. Nothing can: emptiness on one host and history on the other is a contradiction, not an implementation problem.

So the rule is: **every host sweeps forward from `BASE_SEPOLIA_DEPLOY_BLOCK` and shows everything it finds.** Two hosts at the same cursor hold and display the same *swept* rows, checkable by comparing `/api/settlements?limit=1` totals.

**A REFUSAL IS ON-CHAIN TOO, and it took a contract change** (11 Aug 2026, second redeploy of the day). The wallet's policy revert is caught by simulate-before-send and never broadcast, and a reverted transaction carries no logs even if it were — so the refusal rides on the CANCEL, which succeeds. `GantryCore.cancelIntentWithReason(intentId, wallet, reason)` emits `IntentDenied` beside `IntentCancelled`, the indexer sweeps it as a 4th event, and `denials` became chain-derived on every host. Points that bind:
- **`reason` is the wallet's VERBATIM revert data**, not a string or an enum, so the indexer decodes it with `decodeRawError` — the same decoder against the same union the backend used when it caught the revert. One vocabulary at both ends. `rawRevertData` in shared extracts it; `errors.test.ts` pins the round-trip.
- **The indexer re-checks `POLICY_DENIAL_NAMES`** rather than trusting the writer. `decodeRawError` resolves against core + swap + wallet + EIP-3009 errors, so a core-level `IntentExpired` would decode happily and render on a payer's receipt as their agent being refused, with args named against a wallet ABI it does not belong to.
- **`recordDenial` splits PERMANENT from TRANSIENT.** Undecodable bytes return (retrying cannot help); every RPC and disk failure THROWS, so `setCursor` is unreached and the next sweep retries — the contract `IntentSettled` already relies on. Swallowing an RPC blip would advance the cursor past a refusal forever, with `/health` still reporting lag 0.
- **`getIntent` returns the ZERO STRUCT for an unknown id**, so a stale replica would store a denial at a nameless merchant for S$0.00 — and `INSERT OR REPLACE` would let it overwrite a correct row. The status guard throws instead.
- **Agent-door only** (`NotAgentIntent`), the same invariant `settleFromPBM` enforces: a denial on a human QR intent would render as someone's agent being refused on an intent no agent touched. The relayer key can now author an attributed, replicated record naming a third party, and this is what bounds it.
- **A bad reason must never cost the CANCELLATION.** Carrying one adds revert conditions a plain cancel lacks, so `InvalidDenialReason`/`ZeroAddress` retries bare — losing the record, never the cancel. The backend also checks the 256-byte bound before sending; `MAX_DENIAL_REASON_BYTES` lives in shared and a backend test pins it against the regenerated ABI.
- **The residual gap is a failed cancel.** No cancel, no event, so `services/pbm.ts` writes a local fallback row with `cancel_tx: null` rather than lose the refusal — which is also what makes the receipt's "the cancel did not land" branch reachable again. That row is host-local, and it is the only way two hosts can now disagree about a refusal.
- **The sign-off gate covers it now:** `e2e:pbm --expect-denial` asserts the errorReason AND polls `/api/denials?wallet=` for the row. Previously it passed identically whether or not anything was recorded.

**A clean book is a fresh core.** `pnpm contracts:fresh` deploys all four contracts together, pins a new `BASE_SEPOLIA_DEPLOY_BLOCK`, and drops the local database; every host then backfills from that block and they start equal *and stay equal*. That is the whole rehearsal-reset story now: if the book must be empty for a run, deploy. It costs a few minutes and a Vercel rebuild, which is the honest price of a property that holds everywhere rather than on one laptop.

Consequences: `demo:reset` no longer touches the feed (it provisions money, merchants and policy — the name is legacy); `intents` and `denials` are never truncated and grow slowly on a long-lived box; and `/health` carries no "what am I showing" field, because there is nothing left for one to explain.

**`agentPayer` went the same way, and for the same reason** (11 Aug 2026). A bridged x402 `exact` payment hops agent → relayer → core, so the on-chain payer is the RELAYER and the buyer's own address appears nowhere on-chain — only the backend that performed the hop ever knew it, and it wrote that into its own SQLite. So the field was populated on one host and null on every other, and lost on any rebuild: the same "fact the chain cannot re-supply" class as `merchant_profiles`, and the last thing making two backends of the same chain disagree about a settlement. It is replaced by a DERIVED `SettlementEvent.bridged` — `door === "agent" && payer === relayer`, both from the event — computed server-side where the relayer address already lives. Nothing else produces that pair: `settleFromPBM`'s payer is the wallet contract, and a nonce-pinning `exact` client's payer is the agent itself. The UI shows "via facilitator" instead of the burner address, which is information we only ever had half the time; the x402 `PAYMENT-RESPONSE` still reports the real payer, taken from the authorization in hand rather than from storage.

**`pnpm contracts:fresh` is the redeploy, and it is not `demo:reset`.** Run by hand, rarely: it sweeps USDC out of every wallet the redeploy will orphan (live factory *and* `BASE_SEPOLIA_RETIRED_FACTORIES`, and it appends the outgoing factory as it repoints the table, because that blind spot is silent and permanent), runs `DeployAll`, reads the broadcast receipts, and rewrites `addresses.ts` in place — matching contracts by **name**, never by receipt position, so reordering the deploys cannot silently swap two valid-looking addresses. Every precondition (`forge` and `cast` runnable, deploy key present, **deployer === the backend's relayer** or the new core's `onlyRelayer` is wrong forever, Etherscan key) runs *before* anything irreversible. Verification uses `verify-contract` per address, not `forge script --resume --verify`, which demands an unlocked wallet for transactions already mined. `demo:reset` must never redeploy: it has a 30s budget, and rewriting `addresses.ts` would leave the Vercel build (which inlines it) pointing at dead contracts.

**After any redeploy: `pnpm abis`, commit, and rebuild BOTH hosts** — Next inlines addresses at build time, so an un-rebuilt Vercel deployment silently follows a dead contract.

## Status: the public merchant directory (11 Aug 2026)

`/merchants` lists every shop registered on the rail, searchable by name/handle/location, filterable by category, with a detail drawer. Built from a design handoff; **this REOPENS the "no merchant directory" scope decision deliberately** — the objection was that a directory implies curation, and the answer is that it enumerates every registered merchant in registration order, ranks nothing, and says so in its footer. Tests: **191 forge** (186 + 5 skipped fork), **126 shared**, **129 backend** — the current numbers, and the ones the deck quotes. (The forge count moved with the in-flight `IntentDenied` work, not with this change: the directory touches no Solidity.) The five-agent review gate ran over the whole change and every agreed finding was fixed; the three that mattered are recorded below.

**`MerchantRegistered` and `MerchantProfileUpdated` are swept**, taking `SWEPT_EVENTS` from 4 to 6 (the boot assertion moved with it). Free: the pass already reads the core's address in every window and viem compiles the list into one topic0 OR-filter, so both cost **zero extra RPC calls** — the same argument `WalletCreated` made. Registration emits BOTH events in one transaction, so an indexer following one event holds current text without special-casing creation. Rows land in a new swept `merchants` table.

**That deleted the second log walk.** `services/merchants.ts` no longer runs its own bounded 24-window `MerchantRegistered` scan for registration dates: the date is `merchants.block_time`, a local read that survives a restart, and `waitForRegisteredAt` is gone (it existed only to keep a log query off the payment path). `getMerchant` is otherwise unchanged — payout and profile still come from the authoritative chain read behind the 60s TTL.

**The `merchants` table has NO payout column, deliberately.** The directory is a public read surface, and a shop's identity being public does not make the address its money lands in public. Enforced by the schema and pinned by a test, not by whoever writes the next screen; `MerchantSummary` on the wire omits it too. `getMerchant` still reads payout live from the chain for the merchant's own surfaces, which is also the only correct source since a payout can rotate.

**`GET /api/merchants` is unfiltered, unranked and unpaged**, with every row through `resolveProfile` — mandatory, since `registerMerchant` is permissionless and the contract checks length only, so the read path is the only chokepoint standing between an RLO override and a public page. A `total` beside the rows lets a capped response announce itself instead of passing for the whole rail.

**Migration, and it is silent: an existing `gantry.db` permanently omits every merchant registered before the upgrade.** The table starts empty and the cursor never rewinds, so nothing re-reads the blocks those registrations are in — while later ones sweep in normally, which is what makes it look fixed when it is not. `rm packages/backend/gantry.db` (the repo's stated migration) and let it backfill.

Design decisions that differ from the handoff, each for a reason that outlives it:
- **No "accepts agents" badge, and no "take agents" stat.** Nothing on-chain lets a shop opt out of a door — `/api/order/:handle` offers both accepts entries for every handle, and the only thing that can refuse an agent is the payer's own `categoryBitmap` — so the badge would be true on 100% of rows. The card's footer-right slot takes the **registration date** instead, which also makes the oldest-first order legible read down the column; the third stat cell is **Settles in · XSGD**.
- **The drawer says "Registered on-chain", never "Verified on-chain"**, and the chip is neutral. The handoff drew "Verified"; the standing rule wins.
- **No opening hours.** They exist in no struct, table or type, and adding them means a contract redeploy.
- **No payout address in the drawer.** The handoff listed a "Merchant address" row while its own privacy rule forbade one; the rule wins. Rows are Handle · Merchant ID · Category · Registered · Block · Settles in.
- **Every category chip is accent**, as everywhere else in the app. The handoff tinted Food & Beverage alone and greyed the rest, which on a real grid reads as a recommendation — the one thing this page must not do.
- **The wordmark links home and the landing header links here.** The handoff wanted the page terminal; it still links into no authenticated surface, but a page with no way out is a dead end.

**The review gate found one real bug and it was a concurrency one: the WS watch dispatched logs with `void processLog(log)` and no await, so `processLog` reordered them by how much I/O each branch does.** `MerchantRegistered` awaits `blockTime` before inserting; `MerchantProfileUpdated` is pure SQLite. Fired concurrently, the profile UPDATE ALWAYS ran first, matched zero rows, and the merchant was then inserted with empty display text — deterministic, not a race, because an `await` always yields and the loop's next iteration runs in the same turn. A shop that had just onboarded rendered in the directory as its bare handle until the 15s sweep (which awaits each log in order) repaired it. Fixed by serializing the watch through a promise chain (`watchChain`), which also covers any future pair of branches sharing a row. **The general rule: log ORDER only survives if the delivery path is sequential — do not add an `await` to a `processLog` branch and assume ordering still holds.**

**`MerchantListResponse` carries `indexer: {cursor, lag}`, and the empty state is gated on it.** A bare local read cannot tell "the rail is empty" from "this host has not indexed it yet", and the directory does not merely stay silent about the difference — it asserts one ("No shops registered yet"; "a name that isn't here has not been registered"). A cold free-tier instance would print that, fast, with a 200. Deliberately NOT the 503 that `GET /api/agents` raises: that rule exists because an empty answer there makes an agent CLI mint a duplicate wallet, an irreversible on-chain write, and nobody acts on this list — refusing the request would trade a caveated page for no page on the host most likely to be cold when a stranger arrives. `isIndexBehind` in shared owns the threshold (25 blocks: the sweep runs every 15s against ~2s blocks, so a healthy host is always a few blocks back and a tight bound would caveat a current page).

**`resolveProfile` gained the third check the write path always had.** `hasVisibleContent` is now exported and applied on the read path: a display name of nothing but zero-width joiners is neither blank nor deceptive and trims to a non-empty string, so it passed the other two and rendered as an invisible shop name with `displayName ?? handle` never firing. Pre-dated the directory; the directory is what put it on a public page.

Two web-platform notes this cost an afternoon to find, both of which look like broken CSS and are not:
- **Never mix named and arbitrary breakpoint variants on ONE property.** Tailwind sorts `sm:`/`md:` and `min-[1100px]:` into separate blocks, so `sm:text-figure-sm` beat `min-[1100px]:text-hero-sm` at every width and the headline silently never reached 56px. Both steps must take the same form (`min-[640px]:` + `min-[1100px]:`).
- **All three URL params are local state synced with the History API, not router navigations.** A `router.replace` per debounced keystroke queues (each is an RSC round-trip) and the address bar ends up several searches stale — worse than no sync at all, because the stale URL is the one that gets copied. The same argument covers the other two: which drawer is open and which category is selected are decisions the client already made over a list it already holds, so routing them puts a server round-trip in front of rendering state the client authored. `popstate` hands authority back to the URL on Back/Forward. Opening a shop **pushes** and closing it **replaces**, so Back is a way out of the drawer rather than a way back into it. Known limit: a `<Link>` elsewhere pointing at `/merchants?shop=…` would not open the drawer, because nothing re-seeds the state; nothing links that way today.
- **Do not measure UI latency with a timer poll from a background tab.** Chrome clamps `setTimeout` to 1s there, so every interaction reads as ~1000ms and looks like a network round-trip. That sent the URL work down a wrong path once before a `MutationObserver` gave the real figures (drawer open ~30ms, close ~20ms).
- **A `<Suspense>` with no `fallback` renders nothing, and everything below it is excluded from the prerender.** `useSearchParams` forces the boundary, so without a fallback `/merchants` ships empty HTML — no wordmark, no headline — until the bundle hydrates, which on a venue hotspot reads as a broken link. The fallback paints the same chrome and the same loading card the client is about to paint.

Verified in the browser at 1280/1100/768/390: the breakpoint table holds, **1280 no longer scrolls horizontally** (the prototype did), every hit target clears 44×44 below 768, the drawer becomes a bottom sheet, Esc/scrim/Back all close it, focus is trapped while open and restored to the originating card, and `?q=&category=&shop=` all survive a cold load.

## Status: the reachability audit — every on-chain capability now has a door (11 Aug 2026)

An audit asked one question — *what can the contracts do that no screen can reach?* — and found three owner functions that shipped, were tested, and were callable from nowhere. All three are now wired, plus the three places the UI admitted to being unfinished. Tests unchanged (**126 shared, 129 backend, 191 forge / 186 in CI**): the executable changes are confined to `packages/web`, which has no test suite, and none of them touch Solidity (`scripts/contracts-fresh.mjs`, `packages/contracts/.env.example` and the docs also moved, but only as prose). **Verified by `pnpm lint`, `tsc --noEmit` and a production `next build`; the browser paths below are NOT covered by the sign-off gate and must be exercised by hand** — the same gap `agent-writes.ts` already documents for browser-signed writes.

**The three unreachable capabilities, and why each mattered:**
- **`AgentPBMWallet.withdraw`** — a payer funded an agent wallet and had no way to get the money back. Revoke stops the agent spending and **moves nothing**, so a revoked wallet sat on its balance indefinitely; the agents screen rendered that balance next to controls that could not move it. The Funds card on the agent detail screen takes the WHOLE balance to `agent.owner`, with no amount field and no destination field: the only caller the contract accepts is the owner, so the only destination needing no verification is the owner's own, and a free-text `to` on the one screen whose thesis is that funds cannot go astray would be the single place in the app a typo loses money. The copy states the revoke/withdraw distinction explicitly, because collapsing the two leaves a payer believing a revoke returned their money.
- **`AgentPBMWallet.setAgentSigner`** — no session-key rotation, while Q&A answer #3 in the demo script is *about* a stolen session key. The field is now editable on an existing wallet in the Edit-rules form (still locked on one this form just deployed, where the constructor set it moments ago and the policy behind it is not armed yet). **The hint said "Fixed for the life of this wallet", which the contract flatly contradicts** — a false statement in the UI, not merely a missing feature.
- **`GantryCore.setMerchantPayout`** — the Payouts screen explained the rotation rule and offered no control. It is now a real form, and it is **the only write in the merchant back-office**, because it is the only action the chain authenticates for us: `msg.sender == merchant.payout`. Deliberately NOT routed through the backend — a relayer-paid rotation would have to be gated on something the backend knows, and it knows nothing about who a merchant is, which is exactly how a payout becomes rotatable by a stranger holding a handle. There is **no demo-key branch**: the demo key is a PAYER account and is no shop's payout, so offering it would be a guaranteed `NotMerchantPayout` revert dressed as a working button.

**A save can now send THREE transactions** (`setPolicy` → `setAgentSigner` → `setLabel`), ordered by consequence so that whatever a rejected later prompt leaves behind is the half that matters. Only what changed is sent. `signerUnchanged` compares case-insensitively — the field is prefilled from a chain read in EIP-55, and a payer who retypes the same address in lowercase has not asked for a rotation. `validate` now checks the signer on the edit path too: gated on `!wallet` it validated only creation, so an edit could send `setAgentSigner` whatever had been typed, and the contract's only guard is against the zero address. The seven combinations of three optional writes are rendered by `writeList`/`savedText`/`landedText` rather than by a chain of ternaries.

**`lib/confirm-tx.ts` now owns the receipt discipline**, extracted from `agent-writes.ts` when the payout rotation became the second browser-signed write. Same three hazards either way, each of which caused a real bug: viem RESOLVES a reverted receipt rather than throwing, it SILENTLY substitutes a different transaction's receipt via the same-`from`-and-`nonce` scan unless `onReplaced` is passed, and its default wait is three minutes. `UnknownOutcomeError` moved with it and is re-exported from `agent-writes` for the two screens that branch on it. **Adding a write means adding its `what` to those branches** — `unresolvedText` fell through to the policy sentence when `setLabel` arrived and told the payer the wrong transaction was unresolved.

**`policyFingerprint` gained `agentSigner`, and that was not optional.** It is the mechanism that tells "the read has not caught up" from "this is what the chain holds", so a field an owner write can change and the fingerprint does not cover is a field that renders stale with no wait and no notice — and for a signer-only save it would match *instantly*. The field it would have left stale is the one a payer rotating a leaked key is on that screen to check. `revokedFingerprint` takes the signer alongside the label, on the same argument that already applied to the label — a revoke changes neither, so both must carry the value already on-chain. It is **compared lowercase as defence only, and an earlier version of this note gave a false reason for it**: `AgentSummary.agentSigner` comes off a live `agentSigner()` multicall, which viem returns checksummed — it is NOT read from the lowercased swept table, both sides are EIP-55 today, and a literal compare would match. The parameter is typed `Address` rather than `string`, which matters because the form holds the signer as raw input state and the difference between `getAddress(signer.trim())` and the raw field was otherwise invisible to the compiler; passing the raw one yields a fingerprint that can never match, whose symptom is not an error but the detail screen waiting out all six polls and then blaming the RPC.

**Each write records its own expectation, and there is deliberately no single call after all of them.** A terminal call is unreachable the moment an earlier write fails — which is exactly when the expectation matters — and the version that had one left `setAgentSigner` recording nothing at all, so a rotation followed by a failed rename left the store naming the OLD signer, which the detail screen can never match: it hid itself for its whole poll and then blamed the RPC for a bug in the writer. Adding a fourth write means adding its own `record()` call, not extending a final one.

**The stale-read rule applies one cache further out.** `getMerchant` is served from a 60s TTL, so a re-read straight after a confirmed rotation receipt routinely answers with the OLD payout — indistinguishable from the change having failed. A mined receipt outranks a cached read, so `rotatedTo` is rendered until the two agree, with a line saying so. Same argument as `expectAgentPolicy`, different cache. **`withdraw` records no policy expectation** — `policyFingerprint` covers what an owner write can change and never the balance (by design; the balance moves on its own, and folding it in would make every other expectation unsatisfiable), so one recorded there would match instantly and prove nothing. It gets **its own bounded wait instead** (`withdrawal` in `agent-detail.tsx`), and the two mistakes that took are worth keeping written down because both were found only in a browser:

- **The first version had no wait at all**, on the reasoning that a toast could name the lag. It cannot: the main read effect takes its `!expected` branch, reads ONCE, gets a pre-block figure, and never reads again — so the card showed the pre-withdraw balance until the payer navigated away and back, under a toast promising it would catch up.
- **The second version pinned the display to ZERO and never cleared it**, on the reasoning that a mined receipt outranks a lagging read. The receipt is real; the inference was not. It proves **an amount left a wallet that read `before`**, not that the wallet is empty — and `before` can be stale-low, because `demo:reset` tops the PBM wallet up and a deployed build shares one demo key. A surviving remainder then made the exit condition unsatisfiable, so the override stuck, the Withdraw button vanished (it is gated on a non-zero balance) and the screen asserted "this wallet holds no USDC" over real money. **Hiding funds is strictly worse than showing a stale figure**, which is the rule to keep: an optimistic display may only ever claim what the receipt proves (`before − amount`, clamped), any movement in the read ends the wait, and giving up falls back to the chain's answer with a notice rather than freezing a computed one.

**Chain and wallet errors are rendered through `describeWriteError` (`web/src/lib/write-error.ts`), never as `err.message`.** A viem error is a multi-line block — the sentence, then Request Arguments, the contract address, the calldata, a docs URL and a version string — so declining a MetaMask prompt printed sixteen lines of machine detail to say a prompt had been declined. Rules that bind any new call site:
- **Nothing is discarded.** The helper returns `{headline, detail, rejected}` and every caller `console.warn`s the original. Shortening is about what a person reads, never about what is knowable.
- **A contract's own error name travels verbatim.** `CategoryNotAllowed` is the fact and a friendlier clause may sit *alongside* it, never instead of it — the same rule the denial receipts already follow. `CONTRACT_HINT` holds those glosses; an unlisted name still renders, just without one.
- **Shorten at the RENDER site when the raw text is load-bearing upstream.** `pay-flow`'s `pendingTxHash` pulls a transaction hash out of viem's receipt-timeout message with a regex, so trimming it in `fail()` would silently stop matching. The state keeps the whole string; only the `<p>` gets the sentence.
- **`WriteContextError` carries notes as DATA**, not concatenated onto the message: the display layer classifies on the underlying text, and a note glued to the front would either be cut with the block or defeat the matching that shortens it.
- **Match gas exhaustion precisely.** A loose `/insufficient funds|exceeds the balance/` also catches `ERC20: transfer amount exceeds balance`, so a payer short of USDC would be told to top up their ETH. Gas is `insufficient funds for` / `exceeds the balance of the account`.

**Every balance on that screen must come from the one derived `balance`.** The "Balance" row was left reading `agent.balance` directly and the screen stated two different balances at once, seconds after a withdraw.

**Only one effect may own `fresh`.** The withdraw wait re-reads by bumping `reloadNonce` through the main effect rather than calling `api.agent` itself: two effects calling `setFresh` on independent schedules is last-writer-wins, and the losing order is reachable — a lagging withdraw read landing after a revoke's read had settled restores the pre-revoke snapshot and puts an "Active" chip over a revoked wallet.

**Revoke is DISABLED when there is nothing to revoke, never removed.** `revoke()` does not revert on an already-revoked wallet, so a second one costs gas and re-stamps `policyUpdatedAt` for no change — but `status` is derived from data this screen may have already caveated (`waitedOut`), and `chainNow()` falls back to the device clock, so a fast laptop can read a live policy as lapsed. This is the emergency stop for a leaked session key; hiding it on a verdict we have hedged is the worse trade. **Lapsed stays enabled**: expiry stops spending, but the caps and category bitmap are still on-chain and `revoke()` is what clears them.

**The three admitted gaps, closed:**
- **Payouts "By day"** is a real table (`totalsByDay` in `format.ts`): gross, fee, net and count per SGT day, newest first, bucketed on `dayKey` so the split cannot disagree with the header above it. The OLDEST day on screen is the one still being loaded into, so it is named specifically as partial rather than a blanket caveat over rows that are complete.
- **Transactions search covers the whole book.** It searched only the loaded pages, which made the screen's own promise false — a merchant hunting last week's hash got an empty table that looked exactly like no such payment. A `?q=` on `/api/settlements` was the obvious fix and is the WRONG one: half the haystack does not exist in the database (the S$ figures are computed, the days are formatted in SGT, "via facilitator" is derived from payer+door), so SQL `LIKE` would search a strictly NARROWER set while advertising a broader reach. Instead a filter pages the rest of the book in, as a cascade — each page landing re-runs the effect. **The `historyError` guard is load-bearing**: a failed page leaves the cursor put and clears the in-flight flag, so without it the screen retries a failing endpoint as fast as it can answer. Three empty states, never one: still reading / stopped early having read N of M / genuinely no match.
- **"Connect my own wallet"** is real (`lib/payer-signer.ts`). This is NOT the deleted `?burner=1` URL override — that let a query param and an env value disagree silently on a link someone else sent; this is a stored choice made on the payer's own settings screen and stated back to them there. `switchSigner` **reloads the page**, and that is the point rather than laziness: `usePayerIdentity` is called from several components and the payer store memoises against it, so a preference changed in one would leave others signing as the previous account — two live subscriptions disagreeing about who the user is, the exact class of bug that once sent `writeContract` from the wrong account. The preference is hook-internal state inside `usePayerIdentity` (there is no such field on `PayerIdentity`), it is `null` until read from storage, and `ready` is false meanwhile: defaulting to "demo" before the read would sign the first frame as the demo account for a payer who chose their own wallet. **Every consumer must gate on `ready`** — the settings screen did not, and painted the connected branch for one frame on a demo build, with a layout shift, on the one screen whose job is to state which account signs. **Nothing migrates, and the copy says so** — an activity feed is the settlements whose on-chain payer is that address and an agent is a wallet that address owns, so neither is ours to move. A new demo-script failure drill covers the stage risk (a presenter leaving a rehearsal browser switched over).

**`/merchants` had no action at all** — it listed every shop on the rail and offered no way to pay one, a phone book with the numbers removed. The drawer now ends in "Pay this shop" (`/pay/[handle]`, what the printed QR opens) and "Open its shop page" (`/m/[handle]`). The card stays a `<button>`, so no anchor is nested inside one. Both destinations are public payer surfaces, which keeps the standing rule that this page never leads into an authenticated screen.

**`not-found.tsx`, `error.tsx` and `global-error.tsx` exist.** The 404 is reachable from `/qr/[handle]` for an unregistered handle — someone mistyping a shop name while trying to print a standee — and it names that likely mistake and links to the directory rather than being decorative. `error.tsx` replaces Next's blank "Application error: a client-side exception has occurred", which on a projector is indistinguishable from a hung network; it explicitly does NOT claim a payment failed (a render error says nothing about what settled) and offers `reset()` as re-rendering, never as retrying a write. **`global-error.tsx` is inline-styled on purpose**: it REPLACES the root layout, so the fonts, the providers and `globals.css` are all things it may not have — a fallback that depends on the thing it is a fallback for is not one. It is the **third** documented place hex may appear outside `globals.css`, for the same reason as the icon assets: there is no stylesheet to hold a token. Its two colours are `--color-paper` `#f4f2ed` and `--color-ink` `#14150f`; keep them in step by hand.

**RainbowKit's `ConnectButton` is dynamically imported on the Payouts screen.** A static import took that screen's first load from 151 kB to 369 kB — the whole connector modal, for a control most merchants will never touch, on the surface most likely to be left open on a counter behind a venue hotspot. `next/dynamic` with `ssr: false` brings it back to 257 kB; the wagmi hooks the write itself uses are far lighter and stay static. The merchant Overview — the screen that is actually on the projector — is untouched at 151 kB.

**Still deliberately absent after this pass:** a connected (non-demo) payer gets no "Top up" button, which is pre-existing behaviour for connected-wallet mode and unchanged — someone who connected their own wallet can use Circle's faucet. The merchant surface still cannot see denials (documented decision: nothing was ever presented to the shop). `GantryCore.rescueERC20` and the swap's owner functions remain operator-only with no UI, which is correct.

**Live URLs — these are submission artifacts, so treat them as pinned:**

Verified on the deployed pair 9 Aug 2026: `/health` returns `hostClass: "public"` (so `NODE_ENV=production` landed), `chainId 84532`, the expected relayer, indexer lag 0; the backend's CORS preflight answers `access-control-allow-origin: https://gantry-innovatex.vercel.app` rather than `*`; and `/qr/[handle]` encodes the Vercel origin, so `NEXT_PUBLIC_APP_URL` is set.

`NEXT_PUBLIC_BACKEND_URL` was missing from the FIRST Vercel build and was fixed the same day; the shipped bundle now carries `onrender.com` and no `localhost:4000`. Keep the failure shape, because it is silent in a way that wastes an afternoon: an unset var falls back to `http://localhost:4000` (`web/src/lib/env.ts`), so every screen fetches the *visitor's own* machine. Chrome 138+ gates a public origin reaching localhost behind the Local Network Access permission, so the visitor sees an "Access other apps and services on this device" prompt and then "Can't reach the backend / Failed to fetch" whichever button they press. `NEXT_PUBLIC_*` is inlined at build time, so the fix is always **set it and redeploy** — saving it alone changes nothing. **Verify by grepping the built chunks for `onrender.com`, never by reloading the page**, and note the same trap has no fingerprint for `NEXT_PUBLIC_DEMO_KEY`, whose fallback is `undefined`; that one can only be confirmed in the Vercel dashboard.

**Web → Vercel** (import the repo, Root Directory `packages/web`; Vercel detects Next.js). The only committed Vercel config is `packages/web/vercel.json`, and it does exactly one thing — an `installCommand` of `pnpm install --frozen-lockfile --filter @gantry/web...` so the build installs the web package and its workspace deps rather than the whole monorepo. The Dockerfile, `.dockerignore` and root `vercel.json` committed on 8 Aug were **reverted the same day** and stay reverted: Render's native Node deploy needs no container. **Backend → Render free web service** (`pnpm install --frozen-lockfile` / `pnpm --filter @gantry/backend start`, no container).

**The backend cannot be serverless**, and SSE is only the visible half of why: the relayer's nonce counter, the faucet's two legs (a per-address cooldown, an in-flight set and a rolling daily ceiling EACH), the merchant-registration and profile-edit cooldowns, the merchant TTL cache are all in-process, and the indexer holds a WS subscription plus a 15s `setInterval` sweep. It must run as **exactly one instance, never autoscaled** — two would claim the same nonce and halve every rate limit. A persistent disk is NOT needed — the sweep rebuilds `settlements`, `agent_wallets`, `denials` and `merchants`, so a wiped disk costs a cold backfill. The exception is `intents` (not swept) and any denial whose cancel failed, which has no event to re-sweep. A cursor-less indexer re-sweeps from the deploy block in 1,999-block chunks (growing ~43k blocks/day, i.e. ~22 chunks a day; the 11 Aug redeploy reset that floor to block 45328301) — and every one of those chunks is refused by the paid Alchemy endpoint (free tier: **ten** blocks) and served by the public node, so a cold start leans on the rate-limited provider, not the paid one.

**`GET /health` is the host's health-check path, and nothing on it may leave the box** (9 Aug 2026). It returns `{ok, timestamp, uptime, hostClass, chainId, relayer, indexer:{cursor, head, lag, headAt}}` at the cost of one local SQLite read, and makes no RPC call: the host polls this path and restarts the service when it fails, so an awaited `getBlockNumber()` (what it used to do) handed a provider the power to kill an instance mid-sweep. There is deliberately no per-host "what am I showing" field: two hosts at the same `cursor` show the same rows, so `cursor` is the whole answer. The chain facts come from module state the indexer's 15s sweep already records, which is also the better signal: a stale `headAt` means the RPC path is failing, while a growing `lag` means the reads work and the `getLogs` chunks do not. `ok` is liveness only and never folds in a chain verdict. Two fields exist for the deployed host specifically: `uptime` answers "did I just pay a cold start", and `hostClass` is the only way to confirm `NODE_ENV=production` landed once the boot warning has scrolled away — `classifyHost` fails OPEN on a typo.

**The deployed instance is a shop window, not the demo** — the stage run is on the laptop, because payer funding and self-service onboarding only work on a demo host. Render's free-tier spin-down (~50s cold start) therefore costs a browsing screener, not the demo. On the host set `NODE_ENV=production` (caps both faucet legs, closes self-service onboarding, closes unauthenticated profile edits) and `CORS_ORIGIN`. **The Vercel build additionally needs `NEXT_PUBLIC_DEMO_KEY=0x<key>`, `NEXT_PUBLIC_APP_URL`, `NEXT_PUBLIC_BACKEND_URL` and `NEXT_PUBLIC_WALLETCONNECT_PROJECT_ID` set BEFORE the build** (inlined, not runtime-read, so a missing one cannot be fixed without redeploying). Without the demo key the deployed payer page serves only connected wallets, and the whole reason the faucet is capped rather than switched off evaporates. **Understand what that key is before setting it:** `NEXT_PUBLIC_*` is inlined into the client bundle, so it is readable by anyone who opens devtools, and it is a *shared* account — every visitor to the deployed build signs as the same payer and sees the same payment history. That is acceptable only for a demo account holding testnet funds, it belongs on the honest-labels list, and it must never be the relayer's key. The deployed instance must hold the SAME relayer key as the laptop — `GantryCore` stores one `onlyRelayer` address, so a different key cannot create intents. `.github/workflows/ci.yml` (lint, typecheck, both node suites, `forge test`) is kept.

## What's real vs mocked (keep these labels honest everywhere)

Real: all contracts on Sepolia, **payments settle in real Circle USDC** (the payer signs an EIP-3009 authorization against Circle's own contract; the relayer funds the demo payer account and agent wallets by transferring real USDC, not minting), x402 v2 wire format, on-chain PBM denials (contract reverts — never backend if-statements), live LLM tool-use decisions (Gemini free tier; scripted fallback runs the same real wire traffic), real phone + printed QR.
Mocked: MockXSGD — **the only mocked token**, and unavoidable: XSGD exists on no testnet, only on mainnet via StraitsX. MockUSDC was removed from the app on 7 Aug 2026 (the contract stays deployed but unused); owner-set fixed FX rate (GantrySwap skipped — the `IGantrySwap` seam is the production-FX story), single trusted relayer/facilitator key (including the exact-scheme bridge's one-hop custody of agent funds), self-attested merchant categories (no KYC), relayer-paid merchant registration (permissionless on-chain, so faucet trust level — and self-service only on a demo host, because the form spends the relayer's gas key; **nothing anywhere reviews or verifies a merchant**, so never describe the gated deployment as "verified-merchant-only" — that phrase seeded the same false claim into `/onboard`, the README, the config docs and the judges' deck before a review caught it), merchant payout addresses supplied by the merchant rather than issued as passkey smart accounts, no fiat off-ramp.

Added 9 Aug 2026, and each is a real gap rather than an unfinished feature:
- **The merchant back-office is unauthenticated.** There is no merchant login anywhere in Gantry and we are not inventing one, so anyone with the URL can read any shop's takings — and, on a demo host, rewrite its profile text. Say "Registered on-chain", never "Verified on-chain": registration is permissionless and there is no KYC.
- **The demo payer is a single shared account.** On a deployed build every visitor signs with the same key, so the wallet balance, the activity feed and the agents list are shared and the payment history is **not private**. The payer app says so on the wallet and settings screens; the deck and the clip must not imply a per-visitor wallet.
- **A refusal's on-chain record is relayer-ATTESTED, not chain-proven.** `IntentDenied` carries bytes the relayer supplies, so it is not reproducible by a third party: `authorizeSpend` checks the agent's signature FIRST, and that signature is never stored or emitted, so anyone re-simulating gets `InvalidAgentSignature` whatever the real reason was. What IS checkable against public state at that block: `CategoryNotAllowed` against the wallet's `categoryBitmap` and the merchant's `categoryId`, `PerTxCapExceeded` against `perTxCap` and `getIntent().amountIn`, `PolicyExpired` against `expiry`. `DailyCapExceeded` needs archive `spentToday()`; `InsufficientWalletBalance` is not checkable. And the intent stores no wallet, so the wallet↔intent binding is the relayer's word — bounded only by the Agent-door guard. The refusal itself is real; do not claim the record proves it.
- **Merchant profile text is on-chain since 11 Aug 2026 — and still self-attested.** `GantryCore` now stores displayName/location/blurb beside handle/payout/category, so the whole merchant record is a chain fact. **Moving text into a contract changes where it is stored and nothing about whether it is true:** nobody reviews it, there is no KYC, and "on-chain" sitting next to a "Registered" chip is exactly where a reader would hear "verified". Say **self-attested**, and never "verified". The edit route is also still unauthenticated — on a demo host anyone with the URL can rewrite any shop's name, and it now lands on-chain and costs relayer gas rather than a wipeable row.

## Conventions

- pnpm workspaces monorepo. TypeScript everywhere outside `packages/contracts`.
- Everything on `main`, incremental focused commits, Conventional Commits (`feat(contracts): …`). No AI co-author trailers.
- Verify with `pnpm lint` + `tsc --noEmit` (and `forge test` for contracts), not full builds.
- **`e2e:pbm` lives in `packages/agent`, not the backend** — it is `pnpm --filter @gantry/agent e2e:pbm`. Its two siblings (`e2e:pay`, `x402:buy`) are `@gantry/backend`. Naming the wrong package has already sent someone looking in the wrong place; always write the filter out in full.
- **Milestone review gate:** before declaring any milestone (M0–M4) done, run the PR review skill (`pr-review-toolkit:review-pr`) over the milestone's full commit range (e.g. `git diff <last-milestone-tag-or-commit>..HEAD`), triage findings with the user, and fix agreed ones before sign-off. Same applies to any large multi-commit change outside milestones.
- **The repo is PRIVATE** (checked 8 Aug 2026) despite the original "public from day 1" plan. The submission package lists a *public* GitHub repo as one of its five artifacts, so this must flip before submitting or screeners get a 404 — and the Gemini key (which transited a chat) must be rotated BEFORE it flips, not after. Commit history is feasibility evidence for screeners; keep `.env.example` current.
- Demo-script-driven development: if it doesn't appear in the demo script or submission materials, don't build it.
