# Gantry — Project Guide

Hackathon project for NTU InnovateX 2026 (Track 1: Payments & Financial Infrastructure). Solo builder (NTU student, Student Group entry). This file is the canonical context for working sessions — read it fully before building.

## What Gantry is

A payer-agnostic payment rail on stablecoins. One on-chain `PaymentIntent`, one settlement contract, two doors:

- **Human door:** printed static QR encodes `…/pay/<handle>` → mobile payer page → payer signs an EIP-3009 `transferWithAuthorization` (gasless — tourist needs zero ETH) → relayer settles.
- **Agent door:** HTTP `402 Payment Required` with x402 v2 `PAYMENT-REQUIRED` header; `accepts[]` offers the standard `exact` scheme (any vanilla x402 client can pay) AND a custom `gantry-pbm` scheme (agent session key EIP-712 sig, executed through an on-chain policy wallet).

Both settle through `GantryCore._settle()`: pull funds → swap to XSGD if needed (min-out guard) → pay merchant → emit `IntentSettled`. Merchant dashboard shows both payer types landing in one live feed. That convergence IS the thesis — never build anything that exists for only one door except the thin encoding layers.

**Pitch line:** "x402 standardized how machines pay. Gantry is the rail that lets one merchant accept payments from machines and humans alike."

**Framing is strictly Singapore-centric:** XSGD settlement, hawker/tourist scenes, PayNow's structural gaps (no foreign payers, no agent payers), PBM framing after MAS Project Orchid.

The second is the one the payer app promises out loud. Two rules govern them:

- **`invariant = { runs = 48, depth = 96 }` in `foundry.toml` is a CI budget, not a coverage opinion.** At Foundry's default (256×500) this suite took **2056s**, because the handler signs a real EIP-712 authorization and moves tokens on every admitted spend. Before a milestone run the real campaign: `FOUNDRY_PROFILE=deep forge test --match-path "test/*.invariants.t.sol"`.
- **`afterInvariant()` asserts a spend actually succeeded, and it is load-bearing.** Every one of these properties is satisfiable by a wallet that refuses everything, and the first version of the handler was exactly that — warps of up to 3 days marched time past every expiry, so all four passed over an empty set and looked like proof. A handler that stops admitting anything is the default failure mode here, not an exotic one.
- **That same guard made the suite FLAKY, and the fix is in the handler's bounds — never in the guard.** A run could reach zero admitted spends honestly: `rearm` was free to draw a policy admitting nothing (zero per-tx cap, zero daily cap, empty bitmap), and a steered spend was bounded by the per-tx cap while ignoring how much of the daily cap the run had already used. Measured: **5 failed suites in 20 runs**, i.e. a red CI one push in four, on a public repo, for a contract that was never wrong. Now `rearm` always arms something spendable (which costs no coverage — a policy admitting nothing is what `revoke()` produces, and `revokeNow()` is already a fuzz target), and a spend is fully steered until the run lands its first success, aiming at whichever of the per-tx cap and the remaining daily headroom actually binds. Re-measured: **0 in 100**.
- **A single green run proves nothing about a fuzz suite.** This was invisible for a whole session and surfaced only by running the suite in a loop. Any change to the handler, the bounds or `foundry.toml`'s invariant budget gets re-measured the same way — `for i in $(seq 1 30)` with `rm -rf cache/invariant/failures` between runs, because Foundry replays a cached failure and makes a flake look deterministic.

## Architecture (decided — do not relitigate without user)

**Contracts** (`packages/contracts`, Foundry, Solidity ^0.8.24, OZ only for ERC-20/Ownable). **OpenZeppelin comes from npm** (`package.json`, pinned exact to 5.7.0), not `forge install` — OZ's own docs warn a git install can silently follow the unreleased `master` on update, while a published npm version is immutable. Remappings live in **`remappings.txt`, which shadows any CONFLICTING prefix in `foundry.toml`** — a prefix defined only in `foundry.toml` still applies, but one defined in both resolves from `remappings.txt`, so put mappings there to avoid guessing. `forge-std` stays a submodule (test-only, no npm distribution), so a fresh clone needs `git submodule update --init` (not `--recursive`).

- `GantryCore.sol` — merchant registry (`registerMerchant` takes all six fields, so onboarding costs one transaction; `setMerchantPayout` rotation gated on the current payout; `setMerchantProfile` is `onlyRelayer` and provably cannot touch payout, handle or category — an operator who can rename a shop must not be able to redirect its money), `PaymentIntent` lifecycle, `settleWithAuthorization()` (QR + x402 `exact`; **EIP-3009 `nonce` must equal `intentId`** — binds signature to intent), `settleFromPBM()` (Agent-door intents only) and `cancelIntentWithReason()`; shared `_settle` with reentrancy guard, 0.5% protocol fee skim (`feeBps=50`, capped 2%); custom errors; `IntentSettled(intentId, merchantId, payer, tokenIn, amountIn, xsgdOut, feeXsgd, door)` — xsgdOut is gross, merchant receives xsgdOut − feeXsgd. Ownable2Step, renounce disabled.
- `AgentPBMWallet.sol` + permissionless factory — `owner` (the payer) funds it and sets `Policy {uint128 dailyCap, uint128 perTxCap, uint40 expiry, uint256 categoryBitmap}`; `agentSigner` is the agent's session key. `authorizeSpend()` (onlyCore) verifies EIP-712 sig + all policy dimensions + daily window. Custom errors `PerTxCapExceeded`, `DailyCapExceeded`, `CategoryNotAllowed(uint16)`, `PolicyExpired` — these exact names surface in the demo; facilitator returns them as x402 `invalidReason`. Also carries `string label` (owner-set, taken by `createWallet` so naming costs no transaction) and `uint40 policyUpdatedAt` (written by the one internal path `setPolicy` and `revoke` share).
- `FixedRateSwap.sol` (owner-set rate, seeded 1.3421) behind the `IGantrySwap` interface — this is what ships. **`GantrySwap.sol` (x·y=k AMM) is SKIPPED by decision**: do not build, deploy, or wire an AMM unless the user explicitly asks. The seam is the point — production FX means real XSGD liquidity via aggregator/RFQ behind the same interface, not a toy pool. Label the demo rate as owner-set everywhere.
- `MockXSGD.sol` — extends a shared hand-written `EIP3009` base (FiatToken-shaped: typehashes, `authorizationState`, events), 6 decimals, open mint. XSGD carries EIP-3009 deliberately: real XSGD supports x402 natively (StraitsX), and XSGD-direct settlement flows through the same authorization door. XSGD exists on NO testnet — mock is the honest option; label it. (`MockUSDC.sol` survives only as the Foundry suite's generic EIP-3009 test double; it is in no deploy script and no `addresses.ts`.)
- Primary pay token on Sepolia: Circle's real testnet USDC `0x036CbD53842c5426634e7929541eC2318f3dCF7e` (implements EIP-3009, has faucet). Fork-test against it — EIP-3009 domain/sig quirks are a known risk.

**Backend** (`packages/backend`, Node 22 + Express + viem): merchant API; x402-protected routes via `@x402/express` pointed at our own facilitator; facilitator `/verify` + `/settle` (spec-shaped, `@x402/core` types, hand-rolled `gantry-pbm` handler); relayer (holds the only gas key — payers never send transactions); SSE indexer via `watchContractEvent` over WebSocket RPC; paged read surface (`GET /api/settlements`, `/api/denials`, `/api/agents`, `/api/merchants`). SQLite (better-sqlite3) holds four SWEPT tables (`settlements`, `agent_wallets`, `denials`, `merchants`) that any host rebuilds from the chain, and one BACKEND-WRITTEN one (`intents`). Pin `@x402/*` versions (exact `@x402/{core,evm,express,fetch}@2.21.0`); `packages/shared/src/x402.ts` vendors the PAYMENT-REQUIRED/PAYMENT-SIGNATURE codec with zero `@x402` imports as v1→v2 churn insurance (v1 examples online show old `X-PAYMENT` headers — ignore them). **The backend can write no policy** — agent wallets are payer-owned, so there is no `POST /api/policy` and no server key can arm or revoke a spend policy.

Backend orientation: `services/facilitator-core.ts` (pure, config-free: payload schema, `validateExactPayment`, `parseOrderPins`, `splitSignature65`, `reasonForGantryError`) · `services/facilitator.ts` (verify + chain reads with a bounded balance-lag retry) · `services/bridge.ts` (the `exact` bridge + outcome resolution) · `services/pbm.ts` (its non-custodial sibling: denial → simulate revert → decode → `tryCancelIntent` → errorReason) · `services/schemes.ts` (the single scheme dispatch both surfaces call) · `routes/facilitator.ts` (spec HTTP surface: GET `/facilitator/supported`, POST `/verify`+`/settle`, in-band failures) · `routes/order.ts` (DynamicPrice + receipt handler) · `src/x402.ts` (`@x402/express` wired to an **in-process** `FacilitatorClient` — the SDK syncs `/supported` at construction pre-listen, and its HTTP client's default 30s timeout cannot cover three serialized txs). `POST /api/pbm/intent` pre-creates the Agent-door intent the sig must bind, at faucet trust level (it is a relayer-gas vector).

**Agent** (`packages/agent`, Vercel AI SDK `ai`, **two selectable providers**: `@ai-sdk/google` on `gemini-flash-latest` — Google AI Studio free tier, zero-budget decision — or `@ai-sdk/openai-compatible` pointed at AIsa's gateway when `AISA_API_KEY` is set): terminal CLI; tools `list_merchants`, `check_my_policy`, `pay_merchant` (deterministic HTTP + signing inside the tool; the LLM narrates via `streamText` multi-step tool loop). 8s LLM timeout → scripted reasoning fallback, visually identical, hard-gated on `toolCallsStarted === 0` with live-tool lockout so a payment can never run twice. **A live run that ends having called NO tool REFUSES rather than falling back** (`refuseSilentRun`): that is the shape of a gateway answering a tool call as prose in `message.content` while `tool_calls` stays empty — text streams so the timeout never fires, nothing executes so no error is raised, and the agent narrates a purchase it never made. The fallback is provably safe there (`toolCallsStarted === 0`) and still wrong, because the scripted engine **pays** and a model that only talked gave no evidence a payment was wanted. **No wallet address in its config:** it derives its signer from `AGENT_SESSION_KEY` and discovers the wallet it acts for via `GET /api/agents?agentSigner=`, because wallet addresses became dynamic once payers create them. `AGENT_SESSION_KEY` plus a provider key live in `packages/agent/.env` — no provider key ⇒ scripted mode, same beats; AIsa wins when both are set; `AISA_MODEL` is **required and undefaulted** (it must support native tool calling, and a default that 402s mid-demo is worse than a startup error).

**AIsa, verified against the live gateway rather than the docs:** the key authenticates and `GET /v1/models` lists **104 models, of which exactly 6 do not require a paid balance** — the other 98 answer `recharge_required`, including every GPT, Claude and Gemini id. The free ones are `qwen-flash`, `qwen3.7-flash`, `qwen3.7-flash-2026-07-15`, `z-ai/glm-5v-turbo` and two embedding models. **All three free chat models emit proper OpenAI `tool_calls`**, which was the real risk — "OpenAI-compatible" describes an HTTP shape, not function-calling fidelity. `qwen-flash` is what the demo runs on, and **both beats are verified end to end through it**: a real settlement (block 45606773, 181,582 gas) and `CategoryNotAllowed` reported verbatim. Picking a paid id without topping up the account fails at the first tool call, not at startup.

**Gantry's agent CANNOT pay AIsa over x402, and the deck must not say otherwise.** Their marketing says *"every endpoint supports the x402 machine payment protocol"*; what the endpoint actually serves is **MPP, not x402**. Sending `X-MPP-Discovery: true` to a paid model on an unfunded account returns a real challenge — `WWW-Authenticate: Payment … method="tempo"` — whose base64 payload decodes to `{"amount":"10000","currency":"0x20C0…8b50","methodDetails":{"chainId":4217},"recipient":"0xB113…Cc77"}`. **Chain 4217 is Tempo, not Base Sepolia (84532)**, the scheme is `tempo` rather than x402 `exact`, and the token is not Circle USDC. So the PBM wallet cannot fund it and no amount of client work changes that. The true and checkable sponsor claim is the one above: **our agent reasons on AIsa's gateway and settles on our own rail.** Without the discovery header the same request is a plain `recharge_required` 402 with no challenge at all, which is why reading the docs alone would leave this ambiguous. Separate tiny script pays via unmodified `@x402/fetch` (standard-interop proof).

**Chain/infra:** Base Sepolia (`eip155:84532`); **`BASE_SEPOLIA_RPC_URL` is a comma-separated fallback chain** tried in order (one URL is a valid single-entry list), with `https://sepolia.base.org` always appended as last resort. First entry is the primary — the WS URL derives from it. viem's `fallback` **ranking is deliberately OFF**: it would migrate to a lower-latency provider from background samples, so a payment could land on the rate-limited public node while the paid provider is healthy; ordered failover only moves on a real error, which is what we can rehearse. `packages/contracts/.env` must keep a SINGLE url — foundry can't parse the CSV form. There is no Anvil local mode: the backend targets Base Sepolia unconditionally, and the RPC fallback chain is the venue-network insurance.

**BOTH HOSTS AUTO-DEPLOY ON A PUSH TO `main`.** Confirmed 18 Aug by content, not by timing: a push of 30 commits put `GET /pay/:handle` — an endpoint that did not exist before — live on Render, and the new merchant card live on Vercel, with nobody touching a dashboard. **There is no such thing here as "landing work without deploying it."** Three consequences that bind every push:

- **A push is a production event.** Do not push on a presentation day without budgeting for it, and never in the hour before demoing.
- **Every Render deploy wipes SQLite** (free tier, no persistent disk) and triggers a **~35-minute cold backfill** (≈140 chunks × 1,999 blocks at 15s). The swept tables rebuild; `intents` and any failed-cancel denial row do not, and are gone for good. A visitor arriving mid-backfill gets the `isIndexBehind` caveat over a thin feed.
- **A `TOKENS` entry pushed before its token exists on-chain takes PRODUCTION DOWN**, because `assertTokenDomains()` live-reads `name()`/`version()` for every token at boot and exits. The order is strict and not negotiable: deploy the token → `setRate` → *then* push the entry.

**Web → Vercel** (Root Directory `packages/web`). The only committed Vercel config is `packages/web/vercel.json`, doing exactly one thing: an `installCommand` of `pnpm install --frozen-lockfile --filter @gantry/web...` so the build installs the web package and its workspace deps rather than the whole monorepo. **Backend → Render free web service** (`pnpm install --frozen-lockfile` / `pnpm --filter @gantry/backend start`, no container — Render's native Node deploy needs none).

**The backend cannot be serverless**, and SSE is only the visible half of why: the relayer's nonce counter, the faucet's two legs (a per-address cooldown, an in-flight set and a rolling daily ceiling EACH), the merchant-registration and profile-edit cooldowns and the merchant TTL cache are all in-process, and the indexer holds a WS subscription plus a 15s `setInterval` sweep. It must run as **exactly one instance, never autoscaled** — two would claim the same nonce and halve every rate limit. A persistent disk is NOT needed: the sweep rebuilds `settlements`, `agent_wallets`, `denials` and `merchants`, so a wiped disk costs a cold backfill. The exception is `intents` (not swept) and any denial whose cancel failed.

**The deployed instance is a shop window, not the demo** — the stage run is on the laptop, because payer funding and self-service onboarding only work on a demo host. Render's free-tier spin-down (~50s cold start) therefore costs a browsing screener, not the demo — and a keepalive pinger now removes even that (below). On the host set `NODE_ENV=production` (caps both faucet legs, closes self-service onboarding, closes unauthenticated profile edits) and `CORS_ORIGIN`. The deployed instance must hold the SAME relayer key as the laptop — `GantryCore` stores one `onlyRelayer` address, so a different key cannot create intents.

**The deployed backend is kept awake by an off-repo pinger: a cron-job.org job hitting `GET /health` every 10 minutes.** Nothing in this repo configures it, references it, or will notice when it lapses — the only way to check is `uptime` on `/health`, which reads a few hundred seconds on an instance that just woke and hours on one that stayed up. **Ten minutes, not thirty seconds:** spin-down is at 15 minutes idle, so the interval exists to leave slack for a missed check, and a shorter one buys nothing. **It must be external** — a `setInterval` inside the backend could prevent sleep but never end it, since nothing is running to fire it once the instance is down, so any deploy, crash or Render-side restart would leave it asleep until a human arrived. The point is not mainly the 50s: a sleeping instance is not sweeping, so it wakes with a stalled cursor and backfills ~22 chunks per day of sleep at 15s intervals, and a screener landing mid-backfill gets the `isIndexBehind` caveat on `/merchants` over a thin feed. Consequence to hold: the 15s sweep now runs ~5,760×/day against the RPC from Render's shared egress IP instead of stopping overnight.

**`NEXT_PUBLIC_*` is inlined at build time, so every one must be set BEFORE the Vercel build** and a missing one cannot be fixed without redeploying: `NEXT_PUBLIC_DEMO_KEY`, `NEXT_PUBLIC_APP_URL`, `NEXT_PUBLIC_BACKEND_URL`, `NEXT_PUBLIC_WALLETCONNECT_PROJECT_ID`. Keep the failure shape in mind, because it is silent: an unset `NEXT_PUBLIC_BACKEND_URL` falls back to `http://localhost:4000` (`web/src/lib/env.ts`), so every screen fetches the *visitor's own* machine — Chrome 138+ then gates that behind a Local Network Access prompt and the visitor sees "Can't reach the backend / Failed to fetch" whichever button they press. **Verify by grepping the built chunks for `onrender.com`, never by reloading the page.** The same trap has no fingerprint for `NEXT_PUBLIC_DEMO_KEY`, whose fallback is `undefined`; confirm that one in the Vercel dashboard. **Understand what that key is before setting it:** it is readable by anyone who opens devtools, and it is a *shared* account — every visitor signs as the same payer and sees the same history. Acceptable only for a demo account holding testnet funds; it belongs on the honest-labels list; it must never be the relayer's key.

**`GET /health` is the host's health-check path, and nothing on it may leave the box.** It returns `{ok, timestamp, uptime, hostClass, chainId, relayer, indexer:{cursor, head, lag, headAt}}` at the cost of one local SQLite read and makes no RPC call: the host restarts the service when this fails, so an awaited `getBlockNumber()` would hand a provider the power to kill an instance mid-sweep. The chain facts come from module state the 15s sweep already records, which is also the better signal — a stale `headAt` means the RPC path is failing, a growing `lag` means the reads work and the `getLogs` chunks do not. `ok` is liveness only and never folds in a chain verdict. There is deliberately no per-host "what am I showing" field: two hosts at the same `cursor` show the same rows, so `cursor` is the whole answer. `uptime` answers "did I just pay a cold start"; `hostClass` is the only way to confirm `NODE_ENV=production` landed once the boot warning has scrolled away (`classifyHost` fails OPEN on a typo).

### Redeploying

**`pnpm contracts:fresh` is the redeploy, and it is not `demo:reset`.** Run by hand, rarely, never before a demo: it sweeps USDC out of every wallet the redeploy will orphan (live factory *and* `BASE_SEPOLIA_RETIRED_FACTORIES`, appending the outgoing factory as it repoints the table), runs `DeployAll` (the only deploy script — all four contracts in one run), reads the broadcast receipts, and rewrites `addresses.ts` in place — matching contracts by **name**, never by receipt position, so reordering the deploys cannot silently swap two valid-looking addresses. Every precondition (`forge` and `cast` runnable, deploy key present, **deployer === the backend's relayer** or the new core's `onlyRelayer` is wrong forever, Etherscan key) runs *before* anything irreversible. Verification uses `verify-contract` per address, not `forge script --resume --verify`, which demands an unlocked wallet for transactions already mined.

**After any redeploy: `pnpm abis`, commit, and rebuild BOTH hosts** — Next inlines addresses at build time, so an un-rebuilt Vercel deployment silently follows a dead contract. `demo:reset` must never redeploy: it has a 30s budget, and rewriting `addresses.ts` would leave the Vercel build pointing at dead contracts.

## What's real vs mocked (keep these labels honest everywhere)

**Real:** all contracts on Sepolia, **payments settle in real Circle stablecoins — USDC or EURC, the payer chooses** (the payer signs an EIP-3009 authorization against Circle's own contract; the relayer funds the demo payer account and agent wallets by transferring real USDC, not minting), x402 v2 wire format, on-chain PBM denials (contract reverts — never backend if-statements), live LLM tool-use decisions (Gemini free tier, or AIsa's gateway; scripted fallback runs the same real wire traffic), real phone + printed QR.

**Mocked:** MockXSGD — **the only mocked token**, and unavoidable: XSGD exists on no testnet, only on mainnet via StraitsX. Owner-set fixed FX rate (GantrySwap skipped — the `IGantrySwap` seam is the production-FX story). Single trusted relayer/facilitator key (including the exact-scheme bridge's one-hop custody of agent funds). Self-attested merchant categories (no KYC). Relayer-paid merchant registration (permissionless on-chain, so faucet trust level — and self-service only on a demo host, because the form spends the relayer's gas key; **nothing anywhere reviews or verifies a merchant**, so never describe the gated deployment as "verified-merchant-only" — that phrase seeded the same false claim into `/onboard`, the README, the config docs and the judges' deck before a review caught it). Merchant payout addresses supplied by the merchant rather than issued as passkey smart accounts. No fiat off-ramp.

**Real gaps, not unfinished features:**

- **The merchant back-office is unauthenticated.** There is no merchant login anywhere in Gantry and we are not inventing one, so anyone with the URL can read any shop's takings — and, on a demo host, rewrite its profile text.
- **The demo payer is a single shared account.** On a deployed build every visitor signs with the same key, so the wallet balance, the activity feed and the agents list are shared and the payment history is **not private**. The payer app says so on the wallet and settings screens; the deck and the clip must not imply a per-visitor wallet.
- **A refusal's on-chain record is relayer-ATTESTED, not chain-proven.** `IntentDenied` carries bytes the relayer supplies, so it is not reproducible by a third party: `authorizeSpend` checks the agent's signature FIRST, and that signature is never stored or emitted, so anyone re-simulating gets `InvalidAgentSignature` whatever the real reason was. What IS checkable against public state at that block: `CategoryNotAllowed` against the wallet's `categoryBitmap` and the merchant's `categoryId`, `PerTxCapExceeded` against `perTxCap` and `getIntent().amountIn`, `PolicyExpired` against `expiry`. `DailyCapExceeded` needs archive `spentToday()`; `InsufficientWalletBalance` is not checkable. And the intent stores no wallet, so the wallet↔intent binding is the relayer's word — bounded only by the Agent-door guard. The refusal itself is real; do not claim the record proves it.
- **Merchant profile text is on-chain and still self-attested.** Moving text into a contract changes where it is stored and nothing about whether it is true: nobody reviews it, there is no KYC, and "on-chain" sitting next to a "Registered" chip is exactly where a reader would hear "verified". Say **self-attested**, and never "verified". The edit route is also unauthenticated — on a demo host anyone with the URL can rewrite any shop's name, and it lands on-chain and costs relayer gas.

## Rules that bind

### Contracts & settlement

- **`requoteIntent` does NOT cancel, deliberately.** `cancelIntent` is `onlyRelayer`, but the requote route is unauthenticated and takes only an intentId — which `IntentCreated` publishes — so cancelling there lent an `onlyRelayer` capability to anyone watching the chain, killing a payer's already-signed authorization. The superseded intent expires on its own 600s TTL. A local-only `setIntentStatus(cancelled)` is NOT a substitute: `assertNotReplayed` reads it, so the denial survives and merely stops being visible on chain.
- **MockXSGD is not a PAYABLE token** (`TOKENS[...].payable`, `PAYABLE_TOKEN_IDS`). Its `mint()` is public and it is also the settlement token, and the core accepts it as `tokenIn` for XSGD-direct payments — so quoting it on the unauthenticated `POST /api/intents` would let anyone settle a fabricated payment onto any merchant's live book for free. `createIntent` is `onlyRelayer` on-chain, so refusing to quote it closes the path with no contract change.
- Intents are relayer-created with pinned `tokenIn`/`amountIn` quotes; requote = recreate (never mutation). The relayer must only quote no-fee-on-transfer tokens and must **CEIL** the `amountIn` quote (fuzz-proven in `FixedRateSwap.t.sol`).
- `intentId = keccak256(chainid, core, merchantId, nonce)` and doubles as the EIP-3009 nonce. Intent TTL is 600s from **block** timestamp; `validBefore = expiry + 120s`, which bounds the accepted raw-sig front-run window.
- Settlement callers are permissionless. `settleFromPBM` accepts only Agent-door intents; `settleWithAuthorization` serves both doors (x402 `exact` = Agent via the auth door).
- Min-out is enforced via the core's own XSGD balance delta, and the swap allowance is reset after each settle. The 0.5% fee is skimmed in `_settle`, so `xsgdOut` in `IntentSettled` is gross.
- Categories are `uint16 < 256`, for the one-word policy bitmap.
- `FixedRateSwap` accepts only tokens with an owner-listed rate (per-1e6-unit scale, 6dp stables only).
- Real-USDC EIP-712 domain is `("USDC", "2")` and its revert strings are pinned in fork tests.
- **Known accepted vector:** a raw EIP-3009 sig front-run to the token strands funds in core → `rescueERC20` sweep (owner-only; ownership is 2-step and unrenounceable).
- **`getAddress` does NOT validate EIP-55** — it validates shape and re-checksums, silently "fixing" a corrupted paste. `isAddress(a, { strict: true })` is the real check (it accepts all-lowercase, rejects all-uppercase). `setMerchantPayout` is gated on the payout address itself, so a mistyped payout is unrecoverable by anyone — this check is the only thing standing in front of that.

### Secrets in output

- **The RPC credential is in the URL PATH, so the URL IS the secret.** viem's `BaseError.message` is `shortMessage` PLUS `metaMessages`, and a transport failure's metaMessages carry `URL: <rpc url>`; viem's own `getUrl()` strips basic-auth userinfo only, which an Alchemy key is not.
- **Two answers, on purpose** (`src/redact.ts`). `safeMessage()` is EXPLICIT and every wire payload calls it — what crosses a trust boundary is chosen at the call site. Log redaction is installed ONCE at boot, because that half is ~16 `console.error(msg, err)` sites today and every future one is another; `util.inspect` prints the `[cause]` chain, so the log trigger is strictly WIDER than the HTTP one.
- **`redact.ts` imports no config and touches no chain.** `errors.ts` depends on it and `errors.test.ts` pins that invariant, while `config.ts` calls `process.exit(1)` without an RPC URL — importing config there would take the whole suite down in CI. Secrets are registered at boot; unregistered, redaction is the identity.
- **A URL with no path is never registered as a secret.** `sepolia.base.org` is appended to every fallback chain and serves each sweep chunk; redacting its hostname would blind the logs for the endpoint carrying the correctness path.

### Chain access & RPC

- **Alchemy's free tier caps `eth_getLogs` at TEN blocks.** Every 1,999-block sweep chunk is therefore rejected by the paid primary and served by `sepolia.base.org` — two RPC calls per chunk, and **the rate-limited public node is what actually carries the correctness path**. Raising the chunk wedges the sweep entirely (the cursor never advances); dropping it to 10 turns a cold backfill into thousands of calls. The constant has exactly ONE consumer, the indexer sweep.
- **An RPC rate limit belongs to the EGRESS IP, not to the endpoint.** A scan that completes cleanly from a laptop dies on Render's shared IP against the same endpoint, so any concurrency constant tuned locally is a throughput choice and never a safety mechanism, and "swap to a better provider" is unfalsifiable from a laptop. This is why the fix was to fold extra log walks into the one persisted sweep rather than to tune them.
- A cursor-less indexer re-sweeps from the deploy block in 1,999-block chunks, growing ~43k blocks/day (~22 chunks a day), and every one of those leans on the public node — so a cold start is slow by construction.
- **The relayer must not carry an EIP-7702 delegation, and one can appear without anybody deciding to add it.** A wallet UI can upgrade an EOA to a smart account by setting a delegation — MetaMask prompts for exactly that during an ordinary transaction, and the relayer key is a normal account someone may open in MetaMask. Base Sepolia then treats it as delegated and **caps its in-flight transactions**, rejecting the surplus with `-32000 in-flight transaction limit reached for delegated accounts`. This is invisible on every path that sends ONE transaction and waits, which is most of Gantry — and fatal on the **x402 `exact` bridge**, which sends the collect and the settle inside one block window. The symptom is that a spec-compliant client cannot pay us, i.e. exactly the beat that proves standards compliance, while `e2e:pay` and `e2e:pbm` stay green. Detect with `eth_getCode` on the relayer: a plain EOA answers `0x`, a delegated one answers `0xef0100 || delegate`. Fix with **`pnpm --filter @gantry/backend revoke:delegation`**, which signs a 7702 authorization pointing at the zero address. Prefer that over `setRelayer`: it leaves the ADDRESS unchanged, and that address is baked into `addresses.ts`, the Vercel build and the Render env. **Check this before a demo** — it is account state, so nothing in the repo can prevent it recurring.

### Indexer, data & the no-reset rule

- **THERE IS NO RESET. Nothing clears rows, hides rows, or rewinds the cursor** — do not reintroduce it under any name. Every host sweeps forward from `BASE_SEPOLIA_DEPLOY_BLOCK` and shows everything it finds; two hosts at the same cursor hold and display the same swept rows, checkable by comparing `/api/settlements?limit=1` totals. Per-host state is exactly what makes a demo laptop and the deployed backend show different books while indexing the same chain from the same block, and no implementation can fix that — emptiness on one host and history on the other is a contradiction. If the book must be empty for a run, deploy a fresh core.
- **Two paths, one cursor owner:** WS `watchContractEvent` is the latency path; the 15s `getLogs` sweep from the persisted cursor is the correctness path and the sole cursor owner. SSE replay via `Last-Event-ID` = `block:logIndex`; settlements dedup on `(tx_hash, log_index)`.
- **`SWEPT_EVENTS` is 6** (`IntentSettled`, `IntentCancelled`, `IntentDenied`, `WalletCreated`, `MerchantRegistered`, `MerchantProfileUpdated`), with a boot assertion. They cost no extra RPC calls: the pass already reads those addresses in every window and viem compiles the list into one topic0 OR-filter. That is the argument for folding any new log walk in rather than adding a second scan.
- **The WS watch must stay serialized** (`watchChain` promise chain). Log ORDER only survives if the delivery path is sequential — do not add an `await` to a `processLog` branch and assume ordering still holds. Fired concurrently, a branch that awaits I/O (e.g. `blockTime` before insert) always loses to a pure-SQLite branch, which is deterministic, not a race: an `await` always yields and the loop's next iteration runs in the same turn.
- **A failed sweep must never answer "you have no agents" with a 200.** `candidates()` raises 503 `AgentIndexUnavailable`, because an empty list is what makes an agent CLI mint a duplicate wallet. `sweepNow()` waits a running pass out and starts a fresh one — joining an in-flight pass returns a sweep whose head was read before the caller arrived, i.e. blind to exactly the wallet being asked about.
- **`agent_wallets` rows carry their factory** and every read filters on the current one. A row from a retired factory is the dangerous kind of stale: the wallet answers `owner()`/`policy()` perfectly so it lists as healthy, while its immutable `CORE` is the dead core and every payment through it reverts. Unknown-provenance rows default to matching nothing rather than being trusted.
- **The `merchants` table has NO payout column, deliberately** — enforced by the schema and pinned by a test, not by whoever writes the next screen. The directory is a public read surface, and a shop's identity being public does not make the address its money lands in public. `MerchantSummary` omits it too. `getMerchant` reads payout live from the chain for the merchant's own surfaces, which is also the only correct source since a payout can rotate.
- **Addresses are lowercased on WRITE and re-checksummed on the WIRE.** Both halves are deliberate. The store lowercases every id/address column (`db-core.ts`) because its lookups are case-sensitive `=` and a checksummed caller must not cause a silent cache miss — so lowercase is the right KEY. It is the wrong ANSWER: EIP-55 lives entirely in the capitalisation, so a lowercased payer is one nobody can check against Basescan. `checksummed()` (shared/display.ts) is applied in the four row→wire mappers — `toSettlementEvent` (covering the SSE push, the reconnect replay AND the paged read), `denialEventOf`, the signer branch of `candidates()`, `getIntentStatusResponse`. It **passes an unparseable value through instead of throwing**: these mappers are the live feed's only path, so one bad row must cost one field and never the whole page. **Hashes are not addresses and must never be passed to it** — keccak output carries no checksum, so lowercase already is canonical for `txHash`, `intentId` and `merchantId`.
- **`shortAddress` preserves EIP-55 casing** — the checksum lives in the capitalisation, and lowercasing a truncated address destroys the only thing an eyeball can verify against Basescan.
- SQLite is a disposable cache (`db-core.ts` factory). Stored statuses are only `pending`/`settled`/`cancelled` — expired/unknown are computed.
- **`SettlementEvent.bridged` is DERIVED, never stored** (`door === "agent" && payer === relayer`, both from the event, computed server-side where the relayer address lives). A bridged `exact` payment hops agent → relayer → core, so the buyer's own address appears nowhere on-chain and only the backend that performed the hop ever knew it — storing it made the field populated on one host, null on every other, and lost on any rebuild. Nothing else produces that pair: `settleFromPBM`'s payer is the wallet contract, and a nonce-pinning `exact` client's payer is the agent itself. The UI says "via facilitator" rather than showing an address; the x402 `PAYMENT-RESPONSE` still reports the real payer, taken from the authorization in hand rather than from storage.
- **`payer` on `/api/settlements` is a comma-separated list, matched against the on-chain `payer`.** A PBM payment's on-chain payer is the wallet, not the human, so the payer app passes its own address AND its wallets — filtering on the human's alone would hide exactly the rows the agents screen exists to show.
- **`SettlementEvent` carries `logIndex`** so a client merging paged history with the live SSE stream dedupes on `(txHash, logIndex)` — the same primary key the server uses — and any row can mint its own cursor.
- **Migration note:** an existing `gantry.db` from before a table was added permanently omits everything registered before the upgrade — the table starts empty and the cursor never rewinds, while later rows sweep in normally, which is what makes it look fixed when it is not. The fix is `rm packages/backend/gantry.db` and let it backfill.

### On-chain denials

- **A refusal is now re-derivable from public state, and that is a DIFFERENT claim from reproducing it.** `pnpm --filter @gantry/backend verify:denial -- --tx <cancelTxHash>` takes one cancel transaction — the Basescan link a receipt already shows — reads the policy, `spentToday()`, the wallet balance and the merchant's `categoryId` **at that block**, recomputes `authorizeSpend`'s decision through `checkSpend` (shared, `policyCheck.ts`), and compares it to the reason we emitted. It asks no Gantry API for an opinion; every input is a public getter or a log, so a stranger with any RPC URL gets the same answer. Verified working on a 1.4-day-old denial, where the historical read returns a *different* expiry than the wallet has now — which is the proof it is pinned to the block rather than reading head.
  - **It can CONTRADICT us**, and that is the point — a checker that can only agree proves nothing. `auditDenial` returns `consistent` / `contradicted` / `unprovable`, and the fabricated-claim case is unit-tested, not just asserted.
  - **It still does not check the signature**, so it proves the wallet *would have refused* and never that the agent *asked*. `SIGNATURE_IS_NOT_CHECKED` is exported so a caller has to acknowledge that rather than forget it, and the CLI prints it every run. Do not upgrade the wording to "reproducible" or "chain-proven".
  - `checkSpend` evaluates every dimension but reports the FIRST failure in the contract's order, because that is the only reason the chain ever gives. Reordering it would let the checker name a different dimension than the revert did.
- **A denied payment has no reverted transaction.** The policy revert is caught by simulate-before-send and never broadcast, so the refusal rides on the CANCEL, which succeeds: `cancelIntentWithReason(intentId, wallet, reason)` emits `IntentDenied` beside `IntentCancelled`.
- **`reason` is the wallet's VERBATIM revert data**, not a string or an enum, so the indexer decodes it with `decodeRawError` — the same decoder against the same union the backend used when it caught the revert. One vocabulary at both ends. `rawRevertData` in shared extracts it.
- **The indexer re-checks `POLICY_DENIAL_NAMES` rather than trusting the writer.** `decodeRawError` resolves against core + swap + wallet + EIP-3009 errors, so a core-level `IntentExpired` would decode happily and render on a payer's receipt as their agent being refused, with args named against a wallet ABI it does not belong to.
- **`recordDenial` splits PERMANENT from TRANSIENT.** Undecodable bytes return (retrying cannot help); every RPC and disk failure THROWS, so `setCursor` is unreached and the next sweep retries. Swallowing an RPC blip would advance the cursor past a refusal forever, with `/health` still reporting lag 0.
- **`getIntent` returns the ZERO STRUCT for an unknown id**, so a stale replica would store a denial at a nameless merchant for S$0.00 — and `INSERT OR REPLACE` would let it overwrite a correct row. The status guard throws instead.
- **Agent-door only** (`NotAgentIntent`), the same invariant `settleFromPBM` enforces: a denial on a human QR intent would render as someone's agent being refused on an intent no agent touched. The relayer key can author an attributed, replicated record naming a third party, and this is what bounds it.
- **A bad reason must never cost the CANCELLATION.** Carrying one adds revert conditions a plain cancel lacks, so `InvalidDenialReason`/`ZeroAddress` retries bare — losing the record, never the cancel. The backend also checks `MAX_DENIAL_REASON_BYTES` (256, in shared, pinned against the regenerated ABI) before sending.
- **The residual gap is a failed cancel.** No cancel, no event, so `services/pbm.ts` writes a local fallback row with `cancel_tx: null` rather than lose the refusal — which is also what makes the receipt's "the cancel did not land" branch reachable. That row is host-local, and it is the only way two hosts can disagree about a refusal.
- A declined receipt reads "Cancelled · 0x…" from `cancelTxHash` and "Moved: Nothing"; when the cancel itself failed, render no hash at all rather than inventing one. The error name travels **verbatim** (`CategoryNotAllowed`) — the UI may explain it alongside, never instead of.

### x402 & the two doors

- **The facilitator bridge exists because vanilla clients cannot pin the nonce.** `createNonce()` in `@x402/evm` random-generates the EIP-3009 nonce and offers no pinning extension, while the core hardcodes `nonce = intentId` — so a literally-unmodified client can never sign what `settleWithAuthorization` settles. `accepts[]` is therefore 100% spec-standard with `payTo = relayer`; at settle the bridge creates the Agent-door intent, collects the agent's authorization onto the relayer (`transferWithAuthorization`, no pre-float), self-signs an EIP-3009 auth with `nonce = intentId`, and settles via `settlement.settle()`. On-chain payer is the relayer — one custodial hop, PSP-style, on the honest-labels list.
- **Trust channel:** the bridge's order facts (`handle`, `xsgdAmount`) come ONLY from server-pinned `requirements.extra`. The SDK subset-matches extra against the client echo, and the client-echoed `resource.url` is never load-bearing — a client could echo another merchant's URL at the same price. **Any new scheme handler must follow this rule.**
- **Compensation invariant:** never assume "the relayer helper threw ⇒ the tx did not happen" — receipt timeouts leave broadcast txs that may mine. Prove outcomes on-chain before refunding: `authorizationState` reads + the cancel-tx nonce-ordering trick (a cancel that lands proves the stuck tx was consumed; `IntentAlreadySettled` on cancel proves settlement won). Unresolved outcomes get CRITICAL logs with manual-recovery data, never blind refunds. This applies to onboarding too: `registerMerchant` proves ownership on-chain (`ownsHandle`) before reporting failure, and returns `alreadyRegistered` with `txHash: null` — otherwise a register that mined past the 20s receipt cap comes back to its own owner as "that handle is taken".
- **Order facts in `requirements.extra` carry a keyed `pin` and are refused without it.** `handle` and `xsgdAmount` decide which merchant is paid and on `exact` nothing else does — the custodial hop makes `payTo` the relayer for every order, so the payer's signature commits to an amount and a collector, never to a shop. The SDK path is safe (it matches the client echo against the server-built entry), but `POST /facilitator/settle` validates requirements by SHAPE alone. The secret is per-process and random, never config; the digest covers asset and amount so a pin cannot be replayed against another quote, and it must stay **deterministic** — no timestamp, no nonce — because `buildOrderPrice` is deep-equal-matched on the paid retry.
- **A `pbmWallet` must be proven to come from the current factory (`isFactoryWallet`).** Reading `CORE()` off it only looks like provenance: that is a getter, and attacker-written code returns whatever it likes. Without the check the relayer calls `authorizeSpend` on arbitrary code and carries its chosen revert into `cancelIntentWithReason`, letting an attacker author an attributed, chain-replicated `IntentDenied`. The factory's `_walletsOf` is the authority — written inside `createWallet`, unforgeable, current the instant a wallet exists. Fails CLOSED, and sits after the existing wallet reads so a negative is an answer rather than a transport flake. `runPbmSettle` re-verifies, so the one check guards both endpoints.
- **`authorizationState` means "nonce spent", NOT "money moved"** — `cancelAuthorization` sets the same flag and transfers nothing. On the collect path the authorizer is the PAYER, who holds the key, so refunding on the flag alone pays out relayer USDC for a collect that never happened. Prove it with the `AuthorizationUsed` / `AuthorizationCanceled` events (both index authorizer and nonce) over a short window, and **never refund on ambiguous evidence** — log for manual review instead. The sibling check in `resolveFailedSettle` keeps the bare flag legitimately: that authorization is the relayer's own, and only the authorizer can cancel it.
- **`exact` stays accepts[0]** — boot-time assert in `routes/order.ts`, because vanilla clients take the first entry. **BOTH schemes now fan out one entry per payable token** (`OFFER_TOKENS`), so the order is `exact/USDC · exact/EURC · gantry-pbm/USDC · gantry-pbm/EURC` and a standards client can pay in euros. The bridge never needed changing — it reads `requirements.asset` from collect through refund — so the only thing that had made the STANDARDS door dollar-only was that list, while our own scheme already offered both. A **second** boot assert now pins `VANILLA_DEFAULT_TOKEN` as payable: the fan-out is ordered default-first rather than in `PAYABLE_TOKEN_IDS` order, because that order comes from the key order of the `TOKENS` object and tidying the registry would otherwise move every vanilla client onto euros without anyone touching the route.
- **The pay link is ONE URL both a person and a machine can pay**, and it is the shortest proof the project has of its own thesis: `GET /pay/:handle?sgd=4.50` redirects a browser into the payer app and answers everything else with the 402 the agent endpoint would have issued. Both routes share **one `orderAccepts` array by reference**, so the boot asserts cover both doors and neither can drift; `parseOrderResource` accepts both paths for the same reason. Proven with `x402:buy -- --link`, which settles through it with the unmodified client.
- **The negotiation is deliberately stricter than `req.accepts()`.** Express resolves a bare wildcard `Accept` to `text/html`, and a bare wildcard is what curl and most agent HTTP clients send — so the obvious implementation hands an agent a redirect and closes the machine door while every test still passes. `prefersHtml` (`services/pay-link.ts`) requires the client to NAME html, and honours `q=0`.
- **`payerAppOrigin` must never reflect the request host unguarded — that was a live open redirect.** `req.hostname` is the `Host` header, or `X-Forwarded-Host` since the app trusts one proxy hop, so `X-Forwarded-Host: evil.example` moved the `Location` to an attacker's origin *one hop before a payer signs an authorization*, on the URL a QR code points at. Derivation is now allowed only for a private or loopback host (the LAN-scan case it exists for); a public host must set **`APP_URL`**, and without it the route raises `PayLinkNotConfigured` rather than guessing. **It fails CLOSED, so an unset `APP_URL` in production breaks the human half of every charge link** — boot warns, and `/pay/:handle` with `Accept: text/html` returning 500 is the symptom.
- **`GET /discovery/resources` makes the rail enumerable, which is the step an agent had no way to take.** Every other surface assumes a human already chose the shop — they scanned its code or tapped it in a list. This lists every registered merchant as a payable resource, so the loop is: list the shops, pick one, pay it, with no human at any point. It is only available to us because we hold both the registry and the machine door. Proven by `x402:buy -- --discover`, which pays a listing with the unmodified client and knows no handle.
  - **A listing is payable VERBATIM, and that is the invariant.** Each `resource` carries its own `?sgd=1.00` and each `accepts[]` carries the real quote for it (745101 units at the demo rate), so a client pays the published string without parsing it. A placeholder amount would be refused at settle for quoting wrong, which makes discovery decoration — hence the test asserting the exact figure.
  - **`exact` in the default currency stays accepts[0] here too**, for the same reason as the 402 itself.
  - **A listing offers exactly what the challenge it points at offers**, and that is structural rather than remembered: both build from **`OFFER_TOKEN_IDS` in shared** (payable tokens, `VANILLA_DEFAULT_TOKEN` first), so the two cannot drift. They did drift, for the length of one commit — when only `exact` learned to fan out, the listing still advertised dollars alone, and a euro-only agent reading the rail would have concluded the shop could not take its money and never fetched the challenge that said otherwise. Each entry also carries its own quote (745101 USDC / 662252 EURC for S$1.00) and its `extra.name`, so a client selects a currency the same way in a listing and in a challenge.
  - **We are NOT a Bazaar registry and must never say we are.** The response is the x402 Bazaar's `DiscoveryResourcesResponse` shape (`@x402/extensions`, same pinned 2.21.0) served from our own index; nothing publishes to or mirrors anyone else's catalog. Say "a discovery endpoint in the Bazaar's shape".
  - **The origin is derived from the request host, so the response is `no-store`.** Unlike the pay link's redirect this sends nobody anywhere — the caller gets URLs on the host it already chose — but a shared cache must never hand one caller's derived origin to another. A CDN in front of it would need to vary on the forwarded host or be given a pinned origin.
- **The printed standee is NOT the machine door and cannot become one.** It names a shop and no amount, which is why one sheet lasts forever — and an x402 challenge must carry a price. Two places asserted otherwise before the pay link existed; if a third appears, it is wrong. The dual-door URL is always the amount-carrying charge link.
- **`buildOrderPrice` must stay deterministic between challenge and retry** (the middleware deep-equal-matches rebuilt requirements). The owner-set `FixedRateSwap` satisfies this for free; a moving rate would need a short-lived quote pin in the price fn. EVERY accepts entry is a `priceIn(token)` closure over that one function, so a pin added there still fixes all of them.
- **The order confirmation reports the token it was PAID in, or omits the field.** It used to state `USDC` unconditionally, which was true only while `exact` offered nothing else — the first euro payment through that door came back describing itself as dollars. `paidToken()` reads the asset off the PAYMENT-SIGNATURE header the middleware has already verified (`accepted` is subset-matched against the server-built entry before the handler runs, so by then the asset is the server's, not the caller's) and returns null when the header is missing or unreadable. The body is a courtesy — PAYMENT-RESPONSE is the receipt that matters — so an absent field beats a wrong one.
- **`settlement.settle()` is the reusable settle path** — stateless-capable (explicit `validAfter`/`validBefore`, DB fallback). It retries only `isStaleStateRevert` shapes (lagging-replica UnknownIntent / fresh-balance insufficient), 5×1.2s, logged.
- **Never blanket-retry wallet errors:** `isStaleStateRevert` excludes `PBMPullFailed`, `InsufficientWalletBalance` and policy denials (negatively test-pinned).
- **Error vocabulary:** snake_case protocol reasons (`invalid_signature`, `insufficient_funds`, `authorization_already_used`, `quote_changed`, `invalid_requirements`…) plus Gantry custom error names passed through verbatim. Circle's "used or canceled" string maps to `authorization_already_used`; everything else collapses to `settlement_failed` with detail in `errorMessage`. PBM verify-stage adds `unknown_intent`, `intent_expired`, `intent_mismatch`, `intent_already_settled`, `intent_cancelled`, `network_error`; the agent client adds `transport_error` and `outcome_unknown` (the latter means "may have settled; never retry").
- **`gantryErrorsAbi` must include the AgentPBMWallet errors** (`packages/shared/src/errors.ts`) or `CategoryNotAllowed` & co decode as `unknown` and the rejection beat dies. `GantryErrorName` gives compile-time checked names.
- **Wire conventions:** all amounts are 6dp-unit decimal strings; display timestamps (`expiry`, `blockTime`) are unix-second numbers; **`validAfter`/`validBefore` are uint256 decimal strings** that must byte-match the signed typed data. `IntentResponse` field names are deliberately x402 vocabulary (tokenIn=asset, amountIn=amount, payTo=core, intentId=authorization nonce).
- **Relayer:** a single FIFO queue owns the nonce (local counter, resync on any failure including receipt timeout; 20s receipt cap); simulate-before-send everywhere; the wallet client has RPC fallback.
- **Accepted gap:** bridge compensation paths (settle-fails-after-collect → cancel+refund) and `resolveFailedPbmSettle` have no automated coverage.

### Agent wallets & policy

- **The policy binds amount, time, token and CATEGORY — never the PAYEE.** `SpendAuthorization` has three fields and none of them names a merchant; `authorizeSpend` never receives a merchantId, handle or payout, and `intentId` is an opaque keccak the wallet cannot invert. The only payee-adjacent input is `categoryId`, which the core reads from its own registry — and `registerMerchant` takes that from the caller, so it constrains an honest miscategorisation, not a hostile merchant. Say **"the wallet caps how much, when, and what kind of shop — not which shop."** Never let "purpose-bound money" imply a payee allowlist that does not exist.
- **`AGENT_WALLET` is an optional pin, and discovery cannot be made safe without one.** `createWallet` takes `agentSigner` UNPROVEN, so anyone can mint a wallet naming someone else's session key, and the CLI picks the newest active — an attacker can always mint one newer. Nothing is stolen (the EIP-712 domain binds each signature to its own wallet), but the policy constraining the agent silently becomes a stranger's, and no wallet can ever be deleted to undo it.
- **EIP-712 `SpendAuthorization(bytes32 intentId,address token,uint256 amount)`** under domain `{AgentPBMWallet, 1, chainId, wallet}`. Check order is sig → expiry → category → perTx → daily → balance, test-pinned, because these names are read aloud on stage.
- **The cross-stack EIP-712 vector** (`agentPolicy.test.ts` ↔ `test_crossStack_digestVector`, digest `0x1439a3cf…`) pins the TS builder against LIVE contract code (deployCodeTo + live `DOMAIN_SEPARATOR`/typehash reads via PbmDigest). It is an ENCODING pin with hardcoded literals — do **not** "fix" it to read from `addresses.ts` on a redeploy.
- `setPolicy` resets `spentToday` (that is the rehearsal re-arm). `revoke()` zeroes the policy — expiry 0 ⇒ `PolicyExpired`, so there is no separate revoked error. Caps are in token units; S$ is a display conversion via the rate, and must be labeled as such. There is no per-intent ledger; replay leans on the core's Settled-flip (test-documented).
- **`agentStatus()` is the only correct way to badge a policy** — tri-state `active | lapsed | revoked`. `revoked` is derived from `expiry === 0`, so a *naturally lapsed* policy (`0 < expiry < now`) denies every spend while `revoked` stays false; re-deriving the badge by hand renders a dead policy as "Active". The comparison is pinned to `authorizeSpend`, which reverts when `block.timestamp > expiry` — so `expiry` is the LAST second a spend is allowed and `now === expiry` is still active. Pass chain time when you have it: a laptop minutes fast would badge a working policy "lapsed".
- **The daily window rolls at `block.timestamp / 1 days` — UTC days, i.e. 08:00 SGT**, not local midnight. Any copy explaining the cap must say "resets 08:00 SGT".
- **The field is `label`, never `name`** — `DOMAIN_SEPARATOR()` hashes the literal `"AgentPBMWallet"`, and a `name()` getter beside it invites wiring the two together, which would kill every agent signature the moment an owner renamed. It is bounded at **31 BYTES, not characters** (`bytes(label).length`, the inline-string bound): eight 4-byte emoji are already over, so a client counter measuring codepoints would offer a label the contract refuses.
- **Renaming is its OWN transaction.** `setPolicy` must not carry it, because that call resets the daily counter and a rename must never cost the agent its budget.
- `policyUpdatedAt` packs beside `_lastSpendDay`/`_spentToday` (64+128+40 bits, slot 7 offset 24 — verify with `forge inspect AgentPBMWallet storage-layout`), so `_setPolicy` writes the day bucket, the counter and the stamp in one SSTORE. It is out of the `Policy` struct **for the calldata, not for the storage** — a member there would ride in `setPolicy(Policy calldata)` as a caller-supplied field the contract immediately overwrites.
- **A redeploy orphans every wallet the previous factory made** — they still work, nothing lists them — which is accepted whenever the wallet ABI changes, since a factory can only mint what it was compiled against. Reads of newer getters degrade to `""`/`0` rather than marking a wallet unreadable, so an old wallet's policy can still be read and revoked.
- **A mined deploy is proof; a visibility poll after it is best-effort.** `createWallet` has no idempotency — it pushes a fresh wallet on every call — so a throw after the receipt drops an address that exists on-chain, and the caller's retry mints a SECOND wallet for the same signer. Return the address even when the follow-up read cannot see it yet.
- **`GET /api/agents` accepts `owner` and/or `agentSigner`, and requires at least one.** `WalletCreated` indexes both, so filtering by signer costs the same — and that is what lets the agent CLI stop carrying a hardcoded wallet address. An unfiltered list would be every wallet the permissionless factory ever made, so refusing it is not authentication (the chain is public), it is declining to build the aggregate. Creation logs give *candidates*; the live `owner()`/`agentSigner()` reads decide, because ownership is `Ownable2Step` and the signer rotates. **Inherent blind spot:** a wallet transferred *to* you was created naming someone else and is never a candidate.
- Lookups are `walletsOf(owner)` (one `eth_call`, always current — what the payer app needs right after creating a wallet) plus the swept table for signer lookups.
- **The faucet has two legs and they are independent in *reachability*, not just in accounting.** Each owns a rolling-24h ceiling, a per-address cooldown and an in-flight set, all wired in `services/faucet-core.ts` which also owns the constants so a unit test can prove which ceiling each leg got. Two routes, because the two differ in what may refuse them and what a refusal *means*: `POST /api/faucet` (want to **pay** — USDC refusals throw, the gas leg runs first and is reported on a `gas` field) and `POST /api/faucet/gas` (want to **send** — gas refusals throw in gas vocabulary, and the scarce USDC ceiling is never touched). Serial legs meant any USDC refusal made the gas leg unreachable, so a presenter who paid 30s ago got a 429 about USDC when they tapped Revoke. The token leg grants **real Circle stablecoin, sized per token** (a relayer transfer, never a mint) and the payer page caps demo-account amounts at S$5, so one grant always covers the payment it was requested for; the ETH leg targets 0.002 ETH, top-up only, because a key that has never held ETH cannot send an owner transaction. **This does not weaken the payment story** — paying a merchant is still an EIP-3009 signature the relayer submits and costs the payer zero gas. Label it as an owner funding their own wallet.
- Demo prompts must carry the amount ("buy 3 iced teas for the team (S$4.50) from Ah Hock") — an amount-less prompt lets the live model pick its own basket (it once paid its full remaining budget).
- **The AI SDK emits a `start` part before any network I/O**, from the stream's own `start()` callback. Any liveness/timeout logic MUST ignore `start`/`start-step` or it defuses itself ~5ms in. `SYNTHETIC_PARTS` in `packages/agent/src/index.ts` is the guard, and an `AbortController` releases the stalled socket. AI-SDK error parts are rethrown from the stream so the fallback gate owns them.

### Browser-signed writes

- **Never hand viem a bare address as an explicit `account` on a client that signs locally.** An explicit `account` OVERRIDES `client.account`, and `parseAccount` reads a string as a **json-rpc** account — the signal for "the node holds this key" — so `writeContract` calls `eth_sendTransaction` against a plain HTTP transport and the node answers `unknown account`. `simulateContract` only reads `.address`, so simulations pass and the failure looks like an RPC fault. `agent-writes.ts` therefore returns the CLIENT and no separate account, and every call site passes `client.account`.
- **`lib/confirm-tx.ts` owns the receipt discipline**, and all three `waitForTransactionReceipt` hazards it guards have caused real bugs: viem **RESOLVES a reverted receipt** rather than throwing; it **SILENTLY substitutes a different transaction's receipt** via a same-`from`-and-`nonce` scan unless `onReplaced` is passed; and its default wait is three minutes. On the shared demo key — where every visitor of a deployed build signs as one account — that substitution is routine rather than exotic: it would grade a stranger's transaction as our success, and `createWallet` would parse the stranger's logs and hand back their wallet address. Every browser wait passes `onReplaced` and raises `UnknownOutcomeError` — unknown, never failed, because ours never mined. **Adding a write means adding its `what` to `unresolvedText` and the other branches that describe an outcome** — it fell through to the policy sentence when `setLabel` arrived and told the payer the wrong transaction was unresolved.
- **A write the payer signs is confirmed against a DIFFERENT provider than the read that follows it.** The browser waits for its own receipt on its own RPC; every screen then re-reads through the backend on its own fallback chain — so a read issued milliseconds later is routinely served by a replica without the block, and the payer is returned to a screen still showing the rules they just changed, which is indistinguishable from the write doing nothing. The browser holds a mined receipt, so any read that disagrees is behind: record a fingerprint through `expectAgentPolicy` and re-read on a bounded poll until it matches. **Known-superseded data is not rendered at all while that wait runs** — a frame that states the wrong caps is a claim about the chain, and a brief "Your change is on-chain. Reading it back…" is the honest version of the same second. This applies to **revoke** too, where a stale read leaves a chip saying "Active" over a wallet that now reverts everything.
- **`policyFingerprint` must cover every field an owner write can change** — the four policy fields plus `label` and `agentSigner`, and **never** `spentToday` or the balance, which move on their own. A field the fingerprint does not cover renders stale with no wait and no notice, and for a signer-only save it would match *instantly*. It is typed `Address` rather than `string`, which matters because the form holds the signer as raw input state: passing `signer.trim()` instead of `getAddress(signer.trim())` yields a fingerprint that can never match, whose symptom is not an error but the detail screen waiting out all six polls and then blaming the RPC. `revokedFingerprint` takes the signer alongside the label, since a revoke changes neither and both must carry the value already on-chain.
- **Each write records its own expectation; there is deliberately no single call after all of them.** A terminal call is unreachable the moment an earlier write fails — which is exactly when the expectation matters. Adding a fourth write means adding its own `record()` call, not extending a final one.
- **A save can send THREE transactions** (`setPolicy` → `setAgentSigner` → `setLabel`), ordered by consequence so that whatever a rejected later prompt leaves behind is the half that matters. Only what changed is sent. `signerUnchanged` compares case-insensitively — the field is prefilled from a chain read in EIP-55, and a payer who retypes the same address in lowercase has not asked for a rotation. `validate` must check the signer on the edit path too, since the contract's only guard is against the zero address. The seven combinations of three optional writes are rendered by `writeList`/`savedText`/`landedText` rather than by a chain of ternaries.
- **The stale-read rule applies one cache further out.** `getMerchant` is served from a 60s TTL, so a re-read straight after a confirmed payout-rotation receipt routinely answers with the OLD payout — indistinguishable from failure. A mined receipt outranks a cached read, so render `rotatedTo` until the two agree, with a line saying so.
- **`withdraw` records no policy expectation** — the fingerprint covers what an owner write can change and never the balance, so one recorded there would match instantly and prove nothing. It gets **its own bounded wait**, and two mistakes are worth keeping written down because both were found only in a browser: (1) **no wait at all** means the main read effect takes its `!expected` branch, reads ONCE, gets a pre-block figure, and never reads again — the card shows the pre-withdraw balance until the payer navigates away and back; (2) **pinning the display to ZERO** is an inference the receipt does not support — it proves an amount left a wallet that read `before`, not that the wallet is empty, and `before` can be stale-low, so a surviving remainder makes the exit condition unsatisfiable, the Withdraw button vanishes (it is gated on a non-zero balance) and the screen asserts "this wallet holds no USDC" over real money. **Hiding funds is strictly worse than showing a stale figure:** an optimistic display may only claim what the receipt proves (`before − amount`, clamped), any movement in the read ends the wait, and giving up falls back to the chain's answer with a notice rather than freezing a computed one.
- **Only one effect may own `fresh`.** Re-read by bumping a nonce through the main effect rather than calling the API directly: two effects calling `setFresh` on independent schedules is last-writer-wins, and the losing order is reachable — a lagging withdraw read landing after a revoke's read had settled restores the pre-revoke snapshot and puts an "Active" chip over a revoked wallet.
- **Every balance on a screen must come from the one derived `balance`** — reading `agent.balance` directly beside it stated two different balances at once, seconds after a withdraw.
- **Revoke is DISABLED when there is nothing to revoke, never removed.** `revoke()` does not revert on an already-revoked wallet, so a second one costs gas and re-stamps `policyUpdatedAt` for no change — but `status` is derived from data the screen may have already caveated, and `chainNow()` falls back to the device clock, so a fast laptop can read a live policy as lapsed. This is the emergency stop for a leaked session key; hiding it on a verdict we have hedged is the worse trade. **Lapsed stays enabled**: expiry stops spending, but the caps and category bitmap are still on-chain and `revoke()` is what clears them.
- **Withdraw takes the WHOLE balance to `agent.owner`, with no amount field and no destination field.** The only caller the contract accepts is the owner, so the only destination needing no verification is the owner's own, and a free-text `to` on the one screen whose thesis is that funds cannot go astray would be the single place in the app a typo loses money. The copy must state the revoke/withdraw distinction explicitly — revoke stops the agent spending and **moves nothing**, and collapsing the two leaves a payer believing a revoke returned their money.
- **`setMerchantPayout` is the only write in the merchant back-office**, because it is the only action the chain authenticates for us (`msg.sender == merchant.payout`). Deliberately NOT routed through the backend — a relayer-paid rotation would have to be gated on something the backend knows, and it knows nothing about who a merchant is, which is exactly how a payout becomes rotatable by a stranger holding a handle. There is **no demo-key branch**: the demo key is a PAYER account and is no shop's payout, so offering it would be a guaranteed `NotMerchantPayout` revert dressed as a working button.
- **Chain and wallet errors render through `describeWriteError` (`web/src/lib/write-error.ts`), never as `err.message`.** A viem error is a multi-line block — the sentence, then Request Arguments, the contract address, the calldata, a docs URL and a version string — so declining a MetaMask prompt printed sixteen lines of machine detail to say a prompt had been declined. Rules for any new call site:
  - **Nothing is discarded.** The helper returns `{headline, detail, rejected}` and every caller `console.warn`s the original. Shortening is about what a person reads, never about what is knowable.
  - **A contract's own error name travels verbatim.** `CategoryNotAllowed` is the fact and a friendlier clause may sit *alongside* it, never instead of it. `CONTRACT_HINT` holds those glosses; an unlisted name still renders, just without one.
  - **Shorten at the RENDER site when the raw text is load-bearing upstream.** `pay-flow`'s `pendingTxHash` pulls a transaction hash out of viem's receipt-timeout message with a regex, so trimming it in `fail()` would silently stop matching. The state keeps the whole string; only the `<p>` gets the sentence.
  - **`WriteContextError` carries notes as DATA**, not concatenated onto the message: the display layer classifies on the underlying text, and a note glued to the front would either be cut with the block or defeat the matching that shortens it.
  - **Match gas exhaustion precisely.** A loose `/insufficient funds|exceeds the balance/` also catches `ERC20: transfer amount exceeds balance`, so a payer short of USDC would be told to top up their ETH. Gas is `insufficient funds for` / `exceeds the balance of the account`.

### Merchant surfaces

- **The merchant's first screen is Overview, not Settlements.** Both list settlements, so two nav items called "Settlements" and "Transactions" told a merchant nothing about which one they wanted. Overview is the last seven days at a glance plus the live feed; Transactions is the whole book, searchable and exportable. **The `/api/settlements` endpoint, `SettlementEvent`, `settlementsCsv` and the payer store's `settlements` did NOT rename** — those name the data, which is still settlements, and collapsing the two vocabularies would lose the distinction the rename was made to draw.
- **A merchant back-office is always scoped**, because the handle is in the path. `resolveScope` survives to normalise that path segment and to keep `/dashboard?handle=` redirecting correctly.
- **Merchant text is validated on READ, not on write.** Moving the record on-chain removed the only chokepoint that enforced `normalizeProfile`: `registerMerchant` is permissionless and the contract checks length only, so an RLO override, a newline or zero-width padding would render everywhere, and `" "` is truthy so the handle fallback never fires. `resolveProfile` (now in `shared/src/profile.ts`, so the browser can reach it too — a rule only the backend can apply is one the next direct chain read will skip) applies **four** checks, and each was left out once: non-blank, not deceptive, visible, and WITHIN the codepoint ceiling. **Any new writer of merchant text inherits this: validate on read, because you do not control who calls the contract.**
- **The visibility and deception rules are stated against Unicode CATEGORIES, never as codepoint lists.** A blocklist is exactly as complete as whoever wrote it: `U+2060`, `U+00AD`, `U+2061`–`U+2064`, `U+180E` and the `U+E0000` tag block are all invisible and none was on the old one. `isDeceptive` rejects `\p{C}` plus `Zl`/`Zp`; `hasVisibleContent` requires one character outside `\p{C}`, `\p{Z}` and `\p{M}`. **Categories alone are NOT enough:** the Hangul fillers (`U+115F`, `U+1160`, `U+3164`, `U+FFA0`) are `Lo` — LETTERS by category — and render blank, and `U+2800` is `So`; those five are named explicitly because no property escape excludes them. ZWJ/ZWNJ stay legal inside a name, so emoji sequences and decomposed accents still pass.
- **An invisible name is worse than a blank one:** the key is PRESENT, so the `displayName ?? handle` fallback every render site relies on never fires, and a payer's confirm screen reads "Paid to " with nothing after it.
- **The on-chain bound is 4× the clients' codepoint limits** (240/320/560 bytes vs 60/80/140 codepoints): a UTF-8 codepoint is at most 4 bytes, so anything `normalizeProfile` accepts always fits and the client rule stays the binding one. That is the byte-vs-codepoint drift trap the agent `label` documents, avoided by arithmetic instead of by care. `profileFieldLength` counts codepoints, because `String.length` disagrees with the limit on exactly the inputs a live counter warns about.
- **`POST /api/merchants` and `PATCH /api/merchants/:handle` are unauthenticated by decision**, so both carry a `NODE_ENV` host-class gate plus a per-IP cooldown (30s register, 10s edit); a valid `x-admin-token` means an operator (demo-reset seeding) and is exempt. Do not paper this over with a login that checks nothing. `/onboard` branches in the SERVER component, so a production build never ships a working-looking form that 403s after someone has typed their payout address. Gating in production is also the more honest product position: real merchant acquiring is underwritten, never self-service. Draining the gas key stops EVERY door, not just onboarding — the contract stores one `onlyRelayer` address, so the public host and the demo laptop are necessarily the same key.
- **Both write routes validate through the same shared `normalizeProfile` before the tx** — a name we would refuse to store must not cost a permanent handle first. `POST /api/merchants` **requires** `displayName`, `location` and `blurb`: onboarding is the one moment we have the merchant's attention, the handle is claimed permanently, and every payer-facing surface shows the name.
- **An absent registration date renders as nothing**, meaning "the sweep has not reached that block" and never "no such merchant" — an estimate would be worse, since this is the fact a shop would cite as proof it existed. `primeRegistration` writes the row straight from the receipt when a shop onboards through this backend, so it does not wait for the next sweep.
- **`GET /api/merchants` is unfiltered, unranked and unpaged**, with every row through `resolveProfile`. A `total` beside the rows lets a capped response announce itself instead of passing for the whole rail.
- **`MerchantListResponse` carries `indexer: {cursor, lag}` and the empty state is gated on it.** A bare local read cannot tell "the rail is empty" from "this host has not indexed it yet", and the directory does not merely stay silent about the difference — it asserts one ("No shops registered yet"). A cold free-tier instance would print that, fast, with a 200. Deliberately NOT the 503 that `GET /api/agents` raises: that rule exists because an empty answer there makes an agent CLI mint a duplicate wallet, an irreversible on-chain write, and nobody acts on this list — refusing the request would trade a caveated page for no page on the host most likely to be cold when a stranger arrives. `isIndexBehind` in shared owns the threshold (25 blocks: the sweep runs every 15s against ~2s blocks, so a healthy host is always a few blocks back and a tight bound would caveat a current page).
- **Every merchant feed row states its day, and the two surfaces word it differently on purpose.** `feedDay` (Overview) prefers "Today"/"Yesterday" and falls back to "8 Aug"; `tableDay` (Transactions, and `feedDay`'s fallback) is always absolute. Both stack the day above the clock rather than inline, so the column keeps one width and the times stay aligned. A line whose *kind* changes between rows has to be parsed before it can be compared — that is why the feed does not go quiet for today. Transactions stays absolute because a relative label there dates a row against the moment the tab was opened, which is the wrong anchor for a back-office left up on a counter and meaningless in an exported CSV.
- **Transactions search covers the whole book**, by paging the rest of it in as a cascade — each page landing re-runs the effect. A `?q=` on `/api/settlements` is the obvious fix and the WRONG one: half the haystack does not exist in the database (the S$ figures are computed, the days are formatted in SGT, "via facilitator" is derived from payer+door), so SQL `LIKE` would search a strictly NARROWER set while advertising a broader reach. **The `historyError` guard is load-bearing**: a failed page leaves the cursor put and clears the in-flight flag, so without it the screen retries a failing endpoint as fast as it can answer. Three empty states, never one: still reading / stopped early having read N of M / genuinely no match.
- **Payouts "By day"** (`totalsByDay` in `format.ts`) gives gross, fee, net and count per SGT day, newest first, bucketed on `dayKey` so the split cannot disagree with the header above it. The OLDEST day on screen is the one still being loaded into, so it is named specifically as partial rather than a blanket caveat over rows that are complete.
- **The merchant shell mounts a `ToastProvider`, and a successful profile save is a TOAST while a failed one stays inline.** That asymmetry is the rule: a toast is unreadable to anyone who looked away, so a success may be transient and a failure may not. **The merchant viewport must be `fixed`, not the default `absolute`** — the payer app can anchor to its own frame because that frame is `h-dvh overflow-hidden`, but the merchant column is a stretched grid item in document flow, so `bottom-0` would mean the bottom of a page that scrolls well past the viewport. `cn` is tailwind-merge, so passing `fixed` in `viewportClassName` wins.
- **Merchant category is not editable**, because `GantryCore` has no setter for it and a form that silently fails to write the chain is worse than no form. **No logo upload** either — a deterministic tile from the handle, and no blob storage.
- **Payouts frames the absence of a schedule as the feature:** "there is no payout schedule — each payment settles to your address in the same transaction". Do not add a schedule UI to explain something that does not exist.
- **`/merchants` is enumeration, not curation** — it lists EVERY registered merchant in registration order, ranks nothing, and says so in its footer. Hence: no "accepts agents" badge (nothing on-chain lets a shop opt out of a door, so it would be true on 100% of rows — the footer-right slot takes the registration date instead, which also makes the oldest-first order legible read down the column); **every category chip is accent**, since tinting one category and greying the rest reads as a recommendation on a real grid; no opening hours (they exist in no struct, table or type); **no payout address in the drawer**. Rows are Handle · Merchant ID · Category · Registered · Block · Settles in. The drawer ends in "Pay this shop" (`/pay/[handle]`) and "Open its shop page" (`/m/[handle]`) — both public payer surfaces, keeping the rule that this page never leads into an authenticated screen. The card stays a `<button>`, so no anchor is nested inside one.

### Payer app

- **"Connect my own wallet" (`lib/payer-signer.ts`) is a stored preference, not a URL override.** The deleted `?burner=1` let a query param and an env value disagree silently on a link someone else sent; this is a choice made on the payer's own settings screen, kept in `localStorage`, and stated back to them there. `NEXT_PUBLIC_DEMO_KEY` decides what is on *offer* (`0x` + 64 hex ⇒ the pinned demo account is offered; unset/`0` ⇒ connected wallet only; anything else ⇒ off, with a one-time `console.warn`), and the stored choice decides what is in *force*.
- **`switchSigner` reloads the page, and that is the point rather than laziness.** `usePayerIdentity` is called from several components and the payer store memoises against it, so a preference changed in one would leave others signing as the previous account — two live subscriptions disagreeing about who the user is, the exact class of bug that once sent `writeContract` from the wrong account.
- **Every consumer must gate on `ready`.** The preference is hook-internal state inside `usePayerIdentity` (there is no such field on `PayerIdentity`), it is `null` until read from storage, and `ready` is false meanwhile — defaulting to "demo" before the read would sign the first frame as the demo account for a payer who chose their own wallet. The settings screen not gating painted the connected branch for one frame on a demo build, with a layout shift, on the one screen whose job is to state which account signs.
- **Nothing migrates when the signer changes, and the copy says so** — an activity feed is the settlements whose on-chain payer is that address and an agent is a wallet that address owns, so neither is ours to move.
- **A connected (non-demo) payer gets no "Top up" button** — someone who connected their own wallet can use Circle's faucet.

### Web platform traps

- **Never mix named and arbitrary breakpoint variants on ONE property.** Tailwind sorts `sm:`/`md:` and `min-[1100px]:` into separate blocks, so `sm:text-figure-sm` beat `min-[1100px]:text-hero-sm` at every width and a headline silently never reached 56px. Both steps must take the same form (`min-[640px]:` + `min-[1100px]:`).
- **A `<Suspense>` with no `fallback` renders nothing, and everything below it is excluded from the prerender.** `useSearchParams` forces the boundary, so without a fallback the page ships empty HTML — no wordmark, no headline — until the bundle hydrates, which on a venue hotspot reads as a broken link. The fallback must paint the same chrome the client is about to paint.
- **URL params that are client-authored state sync with the History API, not with router navigations.** A `router.replace` per debounced keystroke queues (each is an RSC round-trip) and the address bar ends up several searches stale — worse than no sync at all, because the stale URL is the one that gets copied. Same argument for which drawer is open and which category is selected: decisions the client already made over a list it already holds. `popstate` hands authority back to the URL on Back/Forward. Opening a shop **pushes** and closing it **replaces**, so Back is a way out of the drawer rather than a way back into it. **Known limit:** a `<Link>` pointing at `/merchants?shop=…` would not open the drawer, because nothing re-seeds the state.
- **Do not measure UI latency with a timer poll from a background tab.** Chrome clamps `setTimeout` to 1s there, so every interaction reads as ~1000ms and looks like a network round-trip. Use a `MutationObserver`.
- **`RainbowKit`'s `ConnectButton` is dynamically imported on the Payouts screen.** A static import took that screen's first load from 151 kB to 369 kB — the whole connector modal, for a control most merchants will never touch, on the surface most likely to be left open on a counter behind a venue hotspot. `next/dynamic` with `ssr: false` brings it back to 257 kB; the wagmi hooks the write itself uses are far lighter and stay static. The merchant Overview — the screen actually on the projector — stays at 151 kB.
- **`not-found.tsx`, `error.tsx` and `global-error.tsx` all exist and none is decorative.** The 404 is reachable from `/qr/[handle]` for an unregistered handle — someone mistyping a shop name while trying to print a standee — so it names that likely mistake and links to the directory. `error.tsx` replaces Next's blank "Application error: a client-side exception has occurred", which on a projector is indistinguishable from a hung network; it explicitly does NOT claim a payment failed (a render error says nothing about what settled) and offers `reset()` as re-rendering, never as retrying a write. **`global-error.tsx` is inline-styled on purpose**: it REPLACES the root layout, so the fonts, the providers and `globals.css` are all things it may not have — a fallback that depends on the thing it is a fallback for is not one.
- **Three deliberate exceptions to "no hex outside `globals.css`"**: the static icon assets, `manifest.ts` and `app/global-error.tsx` — each is read by a browser or an OS shell at a moment when no stylesheet exists, so there is no token to reference. Do not "fix" any of the three by inventing one. `global-error.tsx`'s two colours are `--color-paper` `#f4f2ed` and `--color-ink` `#14150f`; keep them in step by hand.

### Copy & honest labels

- **"The wallet caps how much, when, and what kind of shop — not which shop."** The signed `SpendAuthorization` has no payee field; do not let "purpose-bound money" imply an allowlist of merchants.
- **"Registered on-chain", never "Verified on-chain"** — registration is permissionless and self-attested, and "verified" implies a KYC that does not exist.
- Label the FX rate as owner-set everywhere; label MockXSGD as mocked; label the bridge's custodial hop.
- A contract error name is the fact — explain alongside it, never instead of it.

## Paying in more than one currency — what is real

**A payer chooses the currency they PAY IN, and it changes the money, not the labels.** `/app/settings` offers USD and EUR live and INR locked; picking one sets the token on the EIP-3009 authorization, the balance the wallet reads, the rate every S$ figure converts at, and the asset the intent is quoted in. The shop is paid XSGD either way — `GantryCore.XSGD` is `immutable`, so the output cannot vary by screen, by payer or by currency. That is the whole claim: **any currency in, Singapore dollars out.**

**PROVEN END TO END, 19 Aug 2026** — tx `0x0d2c5eaf…`, the first euro payment on this rail. A payer signed an EIP-3009 authorization against Circle EURC, 0.993378 EURC moved payer → core → swap, 1.500000 XSGD came back, and the merchant was paid 1.492500 XSGD after the 0.5% fee. `pnpm --filter @gantry/backend e2e:pay -- --token EURC` repeats it and belongs in the gate beside the USDC run: the flag changes the asset and NOTHING else, which is the claim — if paying in euros needed a second code path it would not be the same door.

**EURC is REAL, and that is the point.** Circle's own EURC on Base Sepolia (`0x808456652fdb597867f38412077A9182bf77359F`) — 6dp, `version "2"`, and a `TRANSFER_WITH_AUTHORIZATION_TYPEHASH` byte-identical to USDC's, which is why the signing path needed no second branch. **No mock was added: MockXSGD is still the only mocked token**, and that sentence stays load-bearing. Listing it took ONE owner transaction — `FixedRateSwap.setRate(EURC, 1_510_000)`, i.e. 1.510000 XSGD per EURC, tx `0x6aded10d…`, 19 Aug 2026 — and no redeploy, because `rateOf` is an open mapping and `GantryCore` holds no token allowlist. The seam the design claimed turned out to be real.

- **SGD is NOT a way to pay and is absent from the picker by construction.** It is the output. `MockXSGD` has an open `mint()` and is `payable: false`, so quoting it would let anyone settle a fabricated payment for free. `PAYABLE_CURRENCY_CODES` is derived from `settleable`, so SGD cannot be re-added by typing it into a component.
- **INR is locked, not hidden.** No INR stablecoin exists on Base Sepolia, so it can never become an `onchain` source here. It stays visible with a "coming soon" toast because "any currency in" is the claim, and a reader deserves to see what is true today AND what is not — rather than a list that quietly implies the set is closed.
- **A stale preference is coerced, not trusted.** The key is `gantry.payCurrency`, NEW on purpose: the old `gantry.displayCurrency` chose a symbol and this chooses a token, and a value stored under the old meaning must never be reinterpreted as a payment instruction. Anything unpayable falls back to USD, and `setPayCurrency` refuses a non-settleable code as a second gate.
- **Both chain reads follow the token, or the feature is a lie.** `sendTokenAddress` is in the dependency array of the balance effect AND the rate effect. Without it a payer switching to euros keeps reading a USDC balance and converting at the USDC rate — ESLint's exhaustive-deps warning is what caught exactly that.
- **The faucet grants the chosen token, sized PER TOKEN, under ONE shared ceiling.** `POST /api/faucet` takes an optional `token`; omitted means USDC, so an older client is unaffected. One ceiling across tokens is deliberate — the scarce thing is the relayer's balance and the abuse surface is identical, so a per-token allowance would just double what a fresh address can drain. The GRANT is per token for the opposite reason: the binding figure is the payer page's S$5 cap converted at that token's rate (3.73 USDC at 1.3421, 3.31 EURC at 1.51), so a flat number is the dollar answer applied to everything — and the waste is not symmetrical, because **USDC is replaceable and EURC is not**. `grantFor()` in `faucet-core.ts` owns it, defaults to `GRANT` so a newly payable token is over-funded rather than refused, and a test pins every payable token's grant against the demo cap through `quoteAmountIn` — the same ceiling-quote the relayer prices with, since a grant that clears a different rounding rule clears nothing. `DEMO_RATE_EURC` in shared exists to make that test meaningful and is a MIRROR of chain state, never the source.
- **`PriceReference` was deleted.** It restated a price in a preview currency, which only made sense while the chosen currency could not be sent. Now the token amount IS the currency amount, so keeping it would print the same number twice.
- **The relayer must HOLD EURC**, because the faucet transfers and cannot mint Circle's token. `demo:reset` reports the shortfall and points at Circle's faucet rather than failing: the USDC spine is unaffected by an empty EURC balance, and silence is what would put a presenter in front of an empty wallet mid-demo.
- **The agent door supports both currencies, one per agent** — see the section below.

### One currency per agent

**An agent wallet spends ONE token, and the constraint is the contract's.** `Policy` holds a single `dailyCap`, a single `perTxCap` and a single `_spentToday` counter, all in "the spend token's own 6dp units" — so a wallet spending two tokens counts €1 as $1, about 13% adrift at 1.51 against 1.3421, and silent about it. `AgentPBMWallet`'s own docstring says as much. Per-token counters would be a wallet change → factory change → all four contracts, so the rule is enforced off-chain instead.

- **The currency is DERIVED from what the wallet holds** (`resolveAgentCurrency`, shared), never stored. The wallet has no field for it, and the alternative — an off-chain table — is exactly the per-host state that makes two hosts disagree about someone's spending rules. `AgentSummary` therefore reports each wallet's own `token`, `balance` and `rate`; a shared `SPEND_TOKEN` constant used to do it, and would now relabel a euro agent's caps in dollars.
- **Enforced at the PBM door, because that is the only path that turns an agent payload into a spend.** `canAgentSpend` refuses a token the wallet does not hold, and refuses a wallet holding two — with its own reason, **`agent_currency_mismatch`**, not the generic `invalid_payload`. That is deliberate: a verify-stage refusal re-challenges, the x402 re-challenge carries only the reason, and our message does not survive the SDK — so the code has to be the explanation or the operator reads "payment rejected at verify (status 402)" and learns nothing.
- **An EMPTY wallet may be quoted in anything.** A default is not evidence; the on-chain balance check refuses it by name (`InsufficientWalletBalance`), which is the specific answer.
- **`accepts[]` carries one entry per payable token for BOTH schemes**, which is what accepts[] is for. `exact/USDC` stays first. A single USDC `gantry-pbm` entry made a euro agent's intent disagree with the offer it was answering, surfacing as `quote_changed` — a confusing way to say "we never offered euros"; `exact` had the same hole one layer out, and until it was closed "any currency in" was true of the two doors we wrote and false of the one anyone else can use. Proven with **`x402:buy -- --token EURC`**, which settles a euro payment through the standards door.
  - **`--token` does not weaken the interop claim, and the script keeps the two spellings visibly apart.** Without the flag the client is literally `new x402Client()` — default selector, first entry, nothing taught. With it, the same class gets its documented `paymentRequirementsSelector` constructor argument, and the selection reads only `extra.name` from the challenge. A single always-on selector would have quietly retired the beat that makes `x402:buy` worth running.
- **Selection is CURRENCY FIRST, then newest-active — in three places, and they must agree.** The agent CLI (`resolveAgentWallet`), `demo-reset`'s provisioning, and `demo-reset`'s step-6b check. When they disagreed, the script armed one wallet and the CLI spent from another; when 6b lagged, it printed a false mismatch warning, which is how a presenter learns to ignore warnings.
- **`topUpPbmWallet` funds the token the wallet ALREADY holds**, and refuses an ambiguous wallet rather than making it worse. It hardcoded USDC, and the first thing it did after a euro agent existed was break it — the provisioning step silently turning a working agent into a refusing one is the failure this rule exists to prevent.
- **Configure with `AGENT_PAY_TOKEN`** in `packages/agent/.env` (unset = USDC, so an agent configured before EURC is unaffected). `AGENT_WALLET` still pins the wallet, and pinning is what the two-agent setup makes necessary rather than merely advisable.
- **A rotated `agentSigner` is NOT discoverable by signer.** The swept `agent_wallets` table is built from `WalletCreated`, which records the signer at creation, so `setAgentSigner` does not update the index — the same blind spot as a wallet transferred to you. Create the wallet with the signer it will use.
- **PROVEN, 19 Aug 2026:** an agent paid a hawker in euros through its policy wallet — tx `0x0013298126…`, 2.980133 EURC in, XSGD to the merchant, on-chain payer the wallet itself. The USDC agent, the denial beat and the verifier are unaffected.

## Known gaps & deliberate absences

Recorded so they are neither re-discovered as bugs nor re-opened as ideas:

- **No automated coverage** for `registerMerchant` itself, for the bridge's compensation paths (settle-fails-after-collect → cancel+refund), or for `resolveFailedPbmSettle` — all chain-touching, matching the repo's convention that the pure parts are covered in shared. `packages/web` has no test suite at all.
- **`lastRegister`/`registerInFlight` are unbounded maps**, and `intents`/`denials` are never truncated — both grow slowly on a long-lived box.
- **Venue NAT collapses every visitor to one per-IP cooldown key.** A room full of people onboarding shops shares the 30s register cooldown; so does a demo laptop behind the same hotspot.
- **No per-IP COOLDOWN on `POST /api/pbm/intent` or `POST /api/intents`** — both now carry a per-IP *in-flight* guard (`services/in-flight.ts`), which bounds parallel abuse but not serial. A cooldown is deliberately not used: venue NAT collapses every visitor to one key, and a presenter paying twice in a row would be 429'd by their own previous payment. No `toWireSpendAuthorization` overloads.
- **The merchant surface cannot see denials** — nothing about a refused agent payment was ever presented to the shop, and that is the decision, not an omission.
- **`GantryCore.rescueERC20` and the swap's owner functions have no UI** and remain operator-only, which is correct.
- **There is no merchant login and we are not inventing one** (see What's real vs mocked).

## Commands & conventions

```bash

pnpm --filter @gantry/web exec tsc --noEmit    # type errors ESLint misses

slither .                      # from packages/contracts; reads slither.config.json, runs in CI
```

- **Slither runs in CI and is GREEN because seven detectors are excluded**, each answered in `docs/security/slither.md` — including two High (`reentrancy-balance`) and three Medium. Read that file before trusting the green: it gates everything *else*, so it is a regression check over the detectors nobody has triaged, never a claim the contracts are correct. The two High findings are the balance-delta min-out guard, and they are false positives **only because both settle entry points are `nonReentrant`** — a hand-rolled `_lock` modifier, since `GantryCore` does not inherit OZ's `ReentrancyGuard` and an inheritance-list reader would conclude there is no guard at all. **If a contract changes, re-open the excluded detectors (`slither . --detect reentrancy-balance`) and re-triage.**
- **Verify with `pnpm lint` + `tsc --noEmit`** (and `forge test` for contracts), not full builds. Never run `next build` while the dev server is running — it clobbers `.next` and the next request 500s on a stale chunk.
- pnpm workspaces monorepo. TypeScript everywhere outside `packages/contracts`.
- Everything on `main`, incremental focused commits, Conventional Commits (`feat(contracts): …`). No AI co-author trailers. Work happens on a short-lived local branch and lands by **rebase then fast-forward**, never a merge commit — 11 branches and 30 commits landed that way on 18 Aug. **A `.git/hooks/pre-push` hook refuses to push anything but `main`** (local, uncommitted, `GANTRY_ALLOW_PUSH=1` overrides); it dates from when feature branches had to stay off a public repo, and it is still the right default now that a push is a deploy.
- **`e2e:pbm` lives in `packages/agent`, not the backend.** Its two siblings (`e2e:pay`, `x402:buy`) are `@gantry/backend`. Naming the wrong package has already sent someone looking in the wrong place; always write the filter out in full.
- **Review gate:** before declaring any milestone or large multi-commit change done, run `pr-review-toolkit:review-pr` over its full commit range, triage findings with the user, and fix agreed ones before sign-off.
- `.github/workflows/ci.yml` runs lint, typecheck, both node suites and `forge test`. Keep it.
- **The repo is PUBLIC** (one of the five submission artifacts) **and a push to `main` deploys both hosts** — see *Live chain & hosts*. Two things follow that did not apply while it was private and hand-landed: **the Gemini key that transited a chat is still unrotated on a public repo**, and anything written here is readable by every other team while the contest is live — so competitive assessments of named rivals stay OUT of the repo.
